## 1. 目标、范围与可信源

本规范的目标是将兽医智能体收束为可审计、可测试、可发布、可回滚的标准业务仓库，并避免领域规则、模型输出、配置参数和部署行为形成多个相互冲突的可信源。

### 1.1 适用范围

- Python 业务代码、API、数据库模型、Alembic 迁移与运行时适配器。
- Agent 编排、临床安全、问诊、记忆、RAG、报告解析和输出审查能力。
- Dockerfile、Docker Compose、服务配置 YAML、环境变量模板和运维脚本。
- GitHub Actions CI/CD、GitHub Release、生产部署和镜像仓库发布。
- 测试、脚本、文档、静态资产和临床安全数据资产。

### 1.2 可信源优先级

发生冲突时，按以下优先级处理：

1. 已发布镜像及其对应 GitHub Release tag。
2. 主分支中的源码、数据库迁移、Docker Compose 和 GitHub Actions 配置。
3. 已部署环境中由密钥管理或 GitHub Environment 下发的真实敏感参数。
4. 本文与其他 `docs/` 文档。
5. 开发样例、临时脚本、未审核静态资产和本地实验结果。

文档不得复制完整运行时配置。业务参数以服务配置 YAML 为准，敏感参数以部署环境中的 env 文件或 GitHub Environment 为准。

## 2. 标准仓库文件树

仓库按业务职责组织，禁止在同一职责范围内建立多个并列可信目录。当前标准结构如下：

```text
.
├── .github/
│   └── workflows/                 # CI、try-run、CD 工作流
├── alembic/
│   └── versions/                  # 业务数据库迁移
├── assets/
│   ├── clinical_safety/           # 已纳入临床安全链路的数据资产
│   └── seeds/                     # 开发或初始化种子数据，不默认构成 CI 硬门禁
├── docker/
│   ├── compose.yml                # 正式环境 Compose 编排
│   ├── compose.dev.yml            # 开发环境 Compose 编排
│   ├── app/                       # Agent API 镜像与运行参数模板
│   ├── litellm/                   # LiteLLM 配置与敏感参数模板
│   ├── mem0/                      # 自托管 Mem0 服务封装
│   ├── mem0-dashboard/            # Mem0 运维 Dashboard 封装
│   └── postgres/                  # PostgreSQL 初始化与运维脚本
├── docs/
│   ├── engineering.md             # 本工程规范
│   ├── docker-compose-dev.md      # 开发环境运维说明
│   ├── docker-compose-production.md
│   └── tickets/                   # 工单、设计结论与历史记录
├── scripts/
│   ├── cd/                        # CD 公共与仓库级脚本
│   ├── ci/                        # CI 公共与仓库级门禁脚本
│   ├── clinical_safety/           # 临床安全资产处理脚本
│   └── dev_payloads/              # 开发手工请求样例，不作为可靠业务资产
├── src/
│   ├── ingress/                   # 接入层、DTO 与边界校验
│   └── vet_agent/
│       ├── agents/                # Agent 能力与问诊编排协作单元
│       ├── api/                   # FastAPI 路由与接口适配
│       ├── clinical_safety/       # 临床安全事件、检索、评估与策略
│       ├── db/                    # SQLAlchemy 模型与数据库能力
│       ├── repositories/          # 规则、知识和持久化读取接口
│       ├── runtime/               # LiteLLM、Embedding 等外部运行时适配
│       ├── services/              # 跨 Agent 的业务服务
│       └── stores/                # 本地或抽象存储实现
├── tests/                         # 单元、集成与链路回归测试
├── vendor/                        # 受版本控制的外部源码，例如 mem0 git submodule
├── pyproject.toml                 # Python 项目、依赖与测试配置
└── uv.lock                        # 依赖锁文件
```

以下内容不得提交到版本库：真实 `.env` 文件、密钥、构建产物、`__pycache__/`、本地数据库卷、临时测试文件和未审核导出数据。

## 3. Git 与发布治理

### 3.1 分支与 Pull Request

1. `main` 只保留可发布、可部署、可回滚状态。
2. 功能开发使用 feature 分支，修复使用 fix 或 hotfix 分支。
3. 功能发布和修复必须通过 Pull Request 合并 `main`。
4. 主分支必须保持线性历史，优先使用 rebase 或 squash 合并。
5. 禁止以日常开发方式直接推送 `main`。
6. Pull Request 必须通过 CI、代码审查和必要的环境审批。

### 3.2 提交与版本

1. 提交描述应与既有历史风格一致，并清晰表达工程意图。
2. 推荐使用 `feat:`、`fix:`、`refactor:`、`test:`、`docs:`、`ci:`、`chore:` 等前缀。
3. 正式版本由 GitHub Release 和 release tag 管理。
4. 禁止新增自定义 release 状态文件、版本 env 文件或平行版本清单。
5. 每个 release tag 必须能唯一解析出应用、Mem0 和 Mem0 Dashboard 镜像 tag。

## 4. Python 代码规范

### 4.1 文件头与编码

1. 所有新增 Python、Shell、YAML、Dockerfile 和 CI/CD 文件必须包含文件头注释块。
2. 文件头至少说明文件路径、作用、职责范围和重要边界。
3. 默认使用 ASCII；只有业务文本、中文注释或既有文件编码确有需要时才引入 Unicode。
4. 注释必须说明复杂业务原因，不得复述显而易见的赋值或控制流程。

Python 文件头示例：

```python
"""
文件：src/vet_agent/services/example.py
作用：提供示例领域服务，负责协调领域对象与外部适配器。
说明：跨包调用必须通过包级公开接口完成，不在本模块直接访问其他包私有实现。
"""
```

### 4.2 严格类型提示

1. 所有函数、方法、闭包、异步函数、类方法、静态方法和回调必须具备完整类型提示。
2. 所有函数必须显式标注返回类型，包括 `-> None`。
3. 容器类型必须参数化，例如 `list[str]`、`dict[str, Any]`、`Mapping[str, str]`。
4. 领域状态应优先使用 `Literal`、`Enum`、Pydantic 字段约束或判别联合类型。
5. `Any` 仅允许位于外部输入边界、第三方库返回值、原始 JSON 或尚未完成建模的过渡层。
6. API 请求、LLM 输出、数据库 JSONB、策略输入输出不得长期使用裸 `dict` 传递。
7. 对外输入和跨层传输优先使用 Pydantic `BaseModel`；内部只读轻量对象可使用 `@dataclass(frozen=True)`。

### 4.3 ReST 风格函数签名注释

所有函数，包括闭包、FastAPI endpoint、Pydantic validator、pytest fixture 和 description 回调，必须使用中文新版标准 ReST 风格注释；不使用 `:type` 字段。

```python
def resolve_policy(event: ClinicalEvent, context: PolicyContext) -> PolicyDecision:
    """根据临床事件与策略上下文生成安全裁决。

    :param event: 已完成结构化归一化的临床事件。
    :param context: 用于裁决的身份、会话和配置上下文。
    :return: 可执行的安全策略决策。
    :raises ValueError: 当事件不满足策略前置条件时抛出。
    """
```

具体要求：

1. 首句描述业务行为，不得仅重复函数名。
2. `:param` 必须覆盖全部参数。
3. `:return:` 必须存在；无返回值时写“无返回值”。
4. 可预期的主动异常使用 `:raises` 描述。
5. 类型由函数签名表达，禁止补写 `:type`。
6. 已有“执行 xxx 业务逻辑”类空泛注释应在重构时逐步替换为具体职责说明。

### 4.4 实现质量

1. 函数应保持单一职责；复杂流程拆分为具名私有函数或领域对象。
2. 不引入无调用路径的工具方法、抽象层或配置项。
3. 未实现的跨领域依赖使用带明确边界的 TODO 空壳，不得跨领域复制实现。
4. 不得以字符串拼接替代可用的结构化 API、解析器或查询构造器。
5. 不得在异常处理中吞掉上下文；应保留可诊断错误信息并按边界转换异常。

## 5. 包边界与分层规范

### 5.1 导入规则

1. 不允许跨包直接导入内部实现模块。
2. 跨包能力必须由目标包的 `__init__.py` 顶层显式暴露。
3. 以下划线开头的函数、类和常量视为私有实现，不得被其他包依赖。
4. 包内实现可以引用本包私有模块，但必须避免循环依赖。

### 5.2 分层方向

```text
ingress/api
    -> orchestrator/agents
        -> services/clinical_safety
            -> repositories/runtime/db/stores
```

该方向用于表达依赖约束，而非要求所有请求经过同一条调用链。低层不得反向引用高层：`services` 不依赖 `api`，`repositories` 不依赖 `agents`，`runtime` 不依赖业务问诊状态。

### 5.3 模型边界

1. 接入 DTO、领域模型、数据库模型、LLM 输出模型和响应模型必须分离。
2. 不得将 ORM 模型直接作为 API 请求或响应契约。
3. LLM 原始输出必须经过结构化模型校验后才能进入业务决策。
4. 策略层的输入和输出必须是稳定、可测试、可序列化的领域模型。

## 6. 配置、容器与部署规范

### 6.1 配置职责划分

| 配置类型 | 存放位置 | 约束 |
|---|---|---|
| 服务非敏感配置 | `application.yml`、`litellm.yml` 等 YAML | 必须有中文注释，说明默认值和运维影响 |
| 敏感参数 | 未提交的 `.env` 文件、GitHub Environment Secrets | 禁止进入 Git、日志和镜像层 |
| 编排参数 | `docker/compose*.yml` 与 compose env 模板 | 仅描述镜像、网络、卷、端口、依赖和挂载 |
| 发布版本 | GitHub Release tag | 禁止以自定义 env 或本地文本文件替代 |

Compose 不得硬编码业务运行参数或敏感值。服务配置参数应通过 YAML 挂载，密钥通过 env 文件注入。

### 6.2 Docker 规范

1. Dockerfile 必须使用多阶段构建，分离构建依赖与运行时依赖。
2. 运行时镜像必须设置工作目录、时区、健康检查和非 root 运行用户。
3. 运行时镜像可包含必要排障工具，但不得无边界增加调试软件。
4. 正式环境 Docker Compose 不得声明 `build`。
5. 正式环境只拉取 CI 已构建并推送到私有镜像仓库的镜像。
6. 第三方官方镜像不可靠时，应基于受版本控制的 `vendor/` 源码封装自有镜像。
7. 不得建立 `deploy/` 等与 `docker/` 并列的生产部署可信目录。

### 6.3 生产部署

1. CD 从 GitHub Release 或手动输入的已发布 release tag 解析镜像。
2. 手动部署仅消费已有 tag 镜像，不得重新构建或覆盖该 tag。
3. 生产服务器只执行镜像拉取、迁移、健康检查和 `docker compose up --no-build`。
4. 真实生产 env 文件由密钥管理流程或人工基线维护，不由 CD 覆盖。
5. 生产操作必须使用 GitHub Environment 审批、最小权限凭据和 SSH 主机指纹校验。

## 7. CI、CD 与测试规范

### 7.1 CI 门禁

CI 必须拆分为可分发的通用门禁和仓库特色门禁。

| 门禁类别 | 主要内容 |
|---|---|
| 通用门禁 | 格式、静态检查、类型检查、测试、锁文件检查、Compose 解析、密钥边界检查 |
| 仓库特色门禁 | API contract、Alembic 迁移、临床安全语义回归、Mem0 封装和运行时配置检查 |
| try-run/dry-run | 可选启动 PostgreSQL、LiteLLM、Mem0 等真实服务进行集成冒烟 |

开发样例 JSON、未审核 RAG chunk、风格不稳定的种子数据和临时静态资产不得作为 CI 硬门禁依据。

### 7.2 测试要求

1. 每个领域 Resolver 必须具备参数化单元测试。
2. API 层必须覆盖入参校验、鉴权、幂等、错误码、附件边界和响应 contract。
3. 数据库迁移必须覆盖升级路径，必要时覆盖兼容与回滚策略。
4. LLM 测试默认使用可控 fake client，不依赖真实模型稳定性。
5. 高风险语义测试必须覆盖肯定、否定、历史、已恢复、他宠、科普、假设、引用、并列和转折。
6. 真实依赖集成测试应独立于快速单元测试，并通过 try-run 或显式工作流触发。

### 7.3 CD 约束

1. GitHub Release 发布时构建并推送不可变 release tag 镜像。
2. CD 只部署已通过 CI 的 release tag。
3. 部署前必须校验 release tag、镜像可用性、生产配置完整性和迁移计划。
4. 部署后必须执行健康检查，并保留失败诊断信息。
5. 生产镜像、Compose、迁移和运行时配置的版本关联必须可追溯。

## 8. Agent、临床安全与数据规范

### 8.1 Agent 决策原则

1. 禁止将关键词命中直接作为最终安全裁决、领域裁决或长期记忆写入依据。
2. 规则只负责召回候选风险；最终决策必须结合结构化事件、主体、否定、时态、事实性和策略条件。
3. LLM 只负责结构化抽取、归一化和辅助生成，不得直接决定不可审计的业务动作。
4. 不确定是合法结果，必须支持 `unknown`、`uncertain`、`needs_confirmation` 等状态。
5. 流程状态只表达下一步业务动作，不得承载复杂医学语义组合。
6. 复杂策略应集中在 Resolver 或声明式策略表中，不得散落在多个 Agent 的字符串判断中。

### 8.2 临床安全

1. 急症、毒物、人药和影像能力边界必须优先保障安全。
2. 安全判断必须区分当前事件、历史事件、已恢复事件、科普咨询、假设问题、引用内容和第三方宠物事件。
3. 否定、转折、并列和多事件表达必须在事件片段级别处理，不得以全文关键词覆盖。
4. 年龄、体重、剂量、时间和检验数值必须结合单位和上下文解析，禁止扫描裸数字作临床裁决。
5. 语义服务不可用时，应降级为确认问题或谨慎提醒；不得将所有词面命中默认升级为紧急状态。
6. 每次安全裁决必须记录候选规则、命中证据、语义证据、拒绝原因、最终动作和 fallback 模式。

### 8.3 附件与报告

1. 用户声明的 `report_type`、附件用途和文件名只能作为路由提示，不得单独作为临床或能力边界事实。
2. 报告分类应结合 MIME、扩展名、上传元数据、解析结果和人工复核策略。
3. 影像诊断不在当前能力范围时，应阻断对应诊断能力，但不得无理由中断基础症状问诊和安全分流。

## 9. RAG、记忆与数据资产规范

### 9.1 RAG

1. RAG 命中只作为回答证据，不得单独作为急症裁决依据。
2. 无检索结果时必须返回空集合，禁止返回前若干条知识伪造检索成功。
3. 检索应采用向量、BM25、重排或结构化过滤；字符重叠等简陋回退只能作为短期兼容方案。
4. 回答引用必须保留来源、资产版本、审核状态和公开引用许可信息。

### 9.2 记忆

1. 长期记忆写入必须经过专门策略校验。
2. 用户提问、假设表达、否定事实、已失效历史事实和未确认自报信息不得写为当前权威事实。
3. 请求侧 `pet_info` 与已验证宠物画像必须分离。
4. mem0 可用作语义记忆后端，但不得作为临床事实的权威来源。
5. 记忆写入必须保留来源、时间、置信度、事实类型、证据片段和冲突处理结果。

### 9.3 数据资产

1. 数据资产必须区分开发样例、候选资产、已审核资产和生产资产。
2. 未审核或不稳定资产不得进入生产安全决策或 CI 硬门禁。
3. 资产变更必须记录来源、版本、审核状态、影响范围和回滚方式。
4. 临床安全资产应由专用脚本、schema 校验和回归测试维护，避免手工编辑破坏结构。

## 10. 日志、审计与安全规范

### 10.1 日志与追踪

1. 每轮请求必须保留 `request_id`、`trace_id`、用户范围、宠物范围和会话范围。
2. 医疗相关安全裁决、记忆写入、RAG 命中和策略拒绝必须输出结构化审计字段。
3. LLM 调用应记录模型名、耗时、fallback、重试和失败原因，但不得记录完整敏感 prompt 或密钥。
4. 异常日志必须可支持故障定位，不得静默吞错。

### 10.2 密钥与访问控制

1. 密钥仅允许存于 GitHub Environment Secrets、部署机密系统或未提交的真实 env 文件。
2. 示例 env 文件只能包含占位符，不得包含真实密钥、真实账户或生产地址。
3. CI 必须执行常见密钥泄露检查。
4. 镜像层、日志、测试输出、文档和错误消息不得泄露密钥。
5. 数据库、对象存储、镜像仓库、模型网关和 SSH 凭据必须遵循最小权限原则。

## 11. 文档与技术债规范

1. 新增服务必须说明本地开发、生产部署、健康检查、常见故障和回滚方式。
2. 抽象策略、复杂配置和跨服务边界必须使用中文解释其目的和运维影响。
3. 文档只描述规范、设计与操作步骤；不得复制成为独立配置可信源。
4. 设计结论、待决事项和技术债必须记录在工单、ADR 或 `docs/tickets/` 中。
5. 文档涉及路径、环境变量、镜像名称或工作流名称时，应在变更实现的同一 Pull Request 中更新。

## 12. 禁止事项与执行检查

以下事项禁止进入主分支：

1. 在生产服务器现场构建应用或中间件镜像。
2. 直接推送主分支导致线性历史被破坏。
3. 跨包直接引用未由 `__init__.py` 公开的内部实现。
4. 新增未写类型提示或未写 ReST 风格函数注释的函数、闭包或回调。
5. 新增没有文件头注释块的源码、脚本、配置或工作流文件。
6. 提交真实密钥、真实 env、构建产物、临时测试文件或未经审核的数据资产。
7. 以关键词命中直接完成临床安全裁决、问诊状态完成或长期记忆写入。
8. 新增无读取点、无使用点、无测试或无文档的配置项。
9. 新增无调用路径的工具方法、抽象层或跨领域实现。
10. 将开发样例、静态 seed 或不稳定资产设为 CI 硬门禁。

合并前最低检查清单：

```text
文件头完整
类型提示完整
ReST 函数注释完整
跨包导入符合边界
配置存在读取点和使用点
测试覆盖新增行为与高风险回归
CI 通过
无真实密钥和临时文件
文档与实际实现一致
```

本规范的核心原则是：以强类型和明确契约约束代码，以单一可信源约束配置和部署，以结构化证据和集中策略约束 Agent 决策，以可审计和可回归测试约束医疗相关风险。
