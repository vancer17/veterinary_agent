# 问诊状态与回答充分性变更总结

> **文档状态**：迁移完成后的对齐基线
>
> **适用范围**：第 11 阶段“问诊状态与回答充分性”、活跃问诊状态存储、回答充分性策略裁决、追问/回答分流、单任务与多任务状态衔接、真实外部 API 集成测试
>
> **不适用范围**：问诊语义抽取内部提示词、RAG 检索与重排、追问问题生成策略、自然语言最终回答生成、长期记忆写入策略、管理后台目录治理、前端交互完整编排

## 1. 变更目的

本次迁移将问诊状态与回答充分性从旧版 `ConsultationStateAgent` 内聚的硬编码状态判断中收束出来，改为“当前会话工作状态 + 结构化证据画像 + OPA 回答充分性裁决 + 显式追问或回答分流”的边界。

迁移前，该阶段存在以下风险：

1. 问诊状态、槽位缺失判断、追问轮数、回答充分性和追问文案混杂在同一层，容易演化为自定义规则状态机。
2. 旧路径可能依赖关键词、正则、模板或固定槽位补全，导致鲁棒性和泛化性下降。
3. 宠物资料、用户本轮陈述、问诊事实、临床安全语义和长期记忆边界不够清晰，存在上下文污染临床推理的风险。
4. 回答充分性缺少独立策略准入，无法稳定审计“为什么本轮追问”或“为什么本轮允许阶段性回答”。
5. 多任务场景下未完成状态的保存、清理和默认状态迁移边界不够稳定。
6. 真实 PostgreSQL、LiteLLM、OPA 等依赖下的纵向 API 验证不足，测试替身结果可能掩盖真实服务契约差异。

迁移后，主链路采用以下边界：

| 能力 | 可信等级 | 位置 | 允许用途 |
|---|---|---|---|
| 活跃问诊状态 | 可信运行状态 | PostgreSQL `consultation_states` 或显式测试仓储 | 保存当前 session/task 尚未完成的问诊工作记忆 |
| 问诊语义结果 | 可信结构化输入 | 问诊语义抽取阶段输出 | 合并核心事实、开放观察和用户意图 |
| 宠物可信画像 | 服务端可信上下文 | 身份、宠物资料与会话范围阶段输出 | 预填稳定身份事实，例如物种、年龄、体重 |
| 临床安全时间语义 | 可信结构化输入 | 临床安全语义抽取阶段输出 | 补充时间证据画像，不替代问诊状态裁决 |
| 证据画像 | 可信策略摘要 | 问诊状态合并之后 | 将已知/未知证据维度投影给 OPA |
| OPA 回答充分性策略 | 可信准入裁决 | `vet_agent.consultation_state.decision` | 只裁决本轮允许阶段性回答，还是必须继续追问 |
| 追问问题 | 用户可见输出候选 | 问诊状态目录与后续 RAG 追问规划 | 组织面向用户的补充问题，不决定回答充分性 |

该阶段只回答“当前任务是否已经具备进入阶段性回答的最低条件；如果不能回答，本轮应追问哪些高价值信息”。它不负责医学诊断、RAG 检索、自然语言最终回答、长期事实写入或前端展示编排。

## 2. 职责边界

### 2.1 问诊状态合并层职责

问诊状态合并层当前负责：

1. 在当前可信用户、宠物、会话和任务范围内恢复上一轮活跃问诊状态。
2. 合并服务端可信宠物画像中的稳定身份事实。
3. 合并问诊语义抽取输出的核心事实、开放观察和用户意图。
4. 合并临床安全链路提供的时间上下文摘要。
5. 构造当前状态、已知证据、未知证据和建议追问槽位的结构化摘要。
6. 将 OPA 裁决结果写入活跃状态与响应 metadata。
7. 根据策略裁决返回“继续追问”或“进入阶段性回答”的统一业务决策。

问诊状态合并层不负责：

1. 使用关键词、正则、用户原文扫描或硬编码短语补造问诊事实。
2. 在模型、数据库或 OPA 不可用时启用本地规则兜底。
3. 把问诊状态保存到 Mem0。
4. 把当前会话工作记忆直接写入长期权威事实。
5. 判断急诊、阻断、升级或其他临床安全动作。
6. 生成最终医学建议文本。
7. 维护可跨任务共享的隐式状态机。

### 2.2 证据画像层职责

证据画像层用于把当前活跃状态投影为回答充分性策略可消费的摘要。

当前稳定证据维度包括：

| 证据维度 | 语义 |
|---|---|
| `patient_identity` | 物种、年龄或体重等身份上下文是否已知 |
| `symptom_profile` | 是否具备主诉或症状补充 |
| `time_course` | 是否具备起病时间或临床安全时间语义 |
| `systemic_status` | 精神状态、食欲饮水等全身状态是否已知 |
| `intake_output` | 食欲、呕吐、大便等摄入排出信息是否已知 |
| `domain_specific` | 当前问诊域相关的呼吸、疼痛、行为或饮食等信息是否已知 |
| `open_observations` | 枚举外开放观察是否存在可用结构化事实 |

证据画像层允许做：

1. 将状态归一为“已知/未知”的证据维度。
2. 输出 `known_categories`、`known_category_count`、`minimum_context`、`advisory_slots` 和 `unresolved_slots`。
3. 为 OPA 提供结构化、可审计且不包含原文扫描逻辑的裁决输入。

证据画像层不允许做：

1. 根据关键词或槽位名称直接决定回答或追问。
2. 把某个单槽位变成固定硬门槛。
3. 根据开放观察类别触发临床安全动作。
4. 代替 OPA 计算最终策略动作。
5. 将“缺槽位”退化为唯一回答充分性标准。

### 2.3 OPA 回答充分性策略职责

OPA 是回答充分性最终准入点，但不是问诊状态机。

OPA 当前负责：

1. 基于结构化状态、结构化意图、证据画像和门槛参数裁决 `answer` 或 `ask`。
2. 输出 `allow`、`mode`、`answer_scope`、`blocking_slots`、`unresolved_slots`、`reason` 和 `reasons`。
3. 在用户明确要求先回答、槽位已完整、语义证据足够或追问轮数达到上限时允许阶段性回答。
4. 在缺少最低上下文或关键高价值证据时要求继续追问。
5. 将策略路径、策略后端和策略输入/结果摘要写入审计 metadata。

OPA 不负责：

1. 读取或扫描用户自然语言原文。
2. 维护多轮问诊状态。
3. 生成追问问题文案。
4. 调用数据库、Mem0、RAG 或模型服务。
5. 执行医学诊断、治疗建议或临床安全动作。
6. 承载关键词库、正则规则或固定槽位状态机。

策略响应必须满足严格契约。OPA 未加载策略、返回缺失字段、字段类型错误或 `action` 与 `allow` 不一致时，应 Fail Fast，不允许被默认为 `answer` 或 `ask`。

### 2.4 追问与回答分流职责

回答充分性策略只决定“是否进入阶段性回答”。主编排层根据裁决进入不同后续链路。

本轮需要追问时：

1. 状态保存为活跃未完成状态。
2. 后续进入追问相关 RAG 与动态追问规划。
3. 响应状态为 `requires_followup`。
4. 单任务响应的 `vet_result.route` 为 `rag_guided_followup`。
5. 不调用最终回答生成 Agent。

本轮可以回答时：

1. 完成状态不再作为活跃未完成状态保留。
2. 后续进入回答相关 RAG 与最终回复生成。
3. 响应状态为 `completed`。
4. 单任务响应的 `vet_result.route` 为 `standard_consultation`。
5. 允许在回答中说明未确认但不再机械阻塞的信息。

多任务场景下，每个任务独立执行上述流程。仅未完成任务继续保存活跃状态，已完成任务从多任务状态集合中移除。

## 3. 数据链位置

问诊状态与回答充分性位于当前 Agent 主数据链的固定位置：

```text
基础输入安全
-> 宠物上下文加载
-> 临床安全语义抽取
-> 临床安全候选召回
-> 临床安全裁决
-> 记忆读取
-> 多任务拆分
-> 问诊语义抽取
-> 问诊状态合并
-> 回答充分性 OPA 策略
-> 追问 RAG 与追问规划，或回答 RAG 与回复生成
-> 输出安全复核
-> 长期记忆候选抽取
-> 长期事实写入
-> 回合留痕
```

该顺序的含义是：

1. 问诊状态不会绕过输入安全、身份范围、临床安全裁决、记忆读取和任务路由。
2. 问诊状态只消费当前任务文本对应的结构化语义结果，不重新拆分任务。
3. 回答充分性裁决发生在 RAG 检索和回复生成之前。
4. RAG 追问规划不能反向改变 OPA 回答充分性裁决。
5. 最终回答生成不能在 `ask` 裁决下被调用。
6. 长期记忆写入只能消费后续记忆候选链路结果，不直接消费活跃问诊状态作为权威事实。

## 4. 接口兼容边界

### 4.1 已覆盖的主业务入口

以下入口继续使用既有请求结构，不要求调用方新增问诊状态或回答充分性字段：

| 接口 | 状态 | 说明 |
|---|---|---|
| `POST /agent/turns` | 已覆盖 | 主业务对话入口，问诊状态与回答充分性在后端主链路内部执行 |
| `POST /openai/v1/responses` | 已覆盖 | OpenAI Responses 风格兼容入口，与主业务入口使用同一问诊状态语义 |

调用方仍按既有契约提交 `input`、`scope_assertion`、`vet_context`、`attachments`、`metadata`、`turn_options` 和 `stream`。调用方不需要显式提交槽位、证据画像或回答充分性策略输入。

### 4.2 保持兼容的请求字段

以下字段为兼容保留，不属于本次迁移的变更面：

| 字段 | 兼容策略 |
|---|---|
| `input` | 继续作为用户本轮原文来源；多任务路径中使用当前任务文本 |
| `scope_assertion` | 继续作为可信用户、宠物和会话范围来源 |
| `vet_context.pet_info` | 继续作为未验证宠物资料兼容字段，不得覆盖服务端可信宠物画像 |
| `attachments` | 继续由输入安全、报告解析或后续能力边界处理，问诊状态不解析附件内容 |
| `metadata` | 继续作为审计透传字段，不得作为问诊状态规则来源 |
| `model` | 继续影响模型选择，不改变问诊状态或 OPA 策略契约 |
| `turn_options.max_followup_questions` | 继续限制本轮最多追问问题数量 |
| `turn_options.idempotency_key` | 幂等语义保持不变 |
| `stream` | 同步与 SSE 流式响应开关保持不变 |

后续如果需要调用方显式传入结构化问诊状态，应通过独立接口契约评审，不应复用 `metadata` 或未验证 `vet_context.pet_info` 作为隐式状态来源。

### 4.3 稳定的响应可观察字段

问诊状态与回答充分性通过响应结构和 metadata 对外可观察。

| 字段或行为 | 语义 |
|---|---|
| `status=requires_followup` | 当前至少一个任务仍需补充问诊信息 |
| `status=completed` | 当前任务或全部任务已经进入阶段性回答 |
| `segments[].type=followup_consultation` | 对应任务输出为追问段落 |
| `segments[].type=medical_consultation` | 对应任务输出为阶段性回答段落 |
| `vet_result.route=rag_guided_followup` | 单任务本轮进入 RAG 辅助追问路径 |
| `vet_result.route=standard_consultation` | 单任务本轮进入标准阶段性回答路径 |
| `vet_result.route=multi_task_consultation` | 本轮按多任务路径执行 |
| `metadata.consultation_phase` | 单任务当前问诊阶段，常见为 `collecting_info` 或 `ready_to_answer` |
| `metadata.consultation_state` | 单任务当前问诊状态摘要 |
| `metadata.consultation_states` | 多任务场景下按任务键组织的未完成状态集合 |
| `metadata.missing_slots` | 单任务本轮策略建议继续追问的槽位 |
| `metadata.answerability` | 单任务回答充分性策略裁决摘要 |
| `metadata.tasks[].answerability` | 多任务中单个任务的回答充分性策略裁决摘要 |
| `metadata.tasks[].missing_slots` | 多任务中单个任务的追问槽位 |
| `metadata.tasks[].consultation_phase` | 多任务中单个任务的问诊阶段 |
| `metadata.followup_question_plan` | 单任务追问规划摘要；仅追问路径存在 |
| `metadata.tasks[].followup_question_plan` | 多任务中单个任务的追问规划摘要 |
| `metadata.multi_agent_path` | 应包含 `ConsultationStateService` 与 `ConsultationAnswerabilityPolicyOPA` |

后续模块可以依赖上述字段进行领域对齐、前端展示和排障，但不应依赖内部类名、提示词正文、模型原始响应、Rego 规则体或测试替身。

### 4.4 活跃问诊状态兼容视图

`consultation_state` 继续作为当前会话问诊工作状态的兼容视图。当前稳定语义如下：

| 字段 | 语义 |
|---|---|
| `chief_complaint` | 当前任务主诉摘要 |
| `domain` | 当前任务问诊域 |
| `phase` | 当前问诊阶段 |
| `slots` | 从可信核心事实和可信宠物画像派生的紧凑兼容槽位视图 |
| `working_facts` | 当前会话范围内的核心事实工作记忆 |
| `observations` | 当前会话范围内的开放观察工作记忆 |
| `asked_questions` | 当前任务已问过的追问问题 |
| `followup_rounds` | 当前任务连续追问轮数 |
| `evidence_profile` | 回答充分性策略输入的证据画像摘要 |
| `answerability` | 最近一次回答充分性裁决摘要 |
| `user_intent` | 本轮可信用户意图摘要 |
| `semantic_extraction` | 本轮问诊语义抽取审计摘要 |
| `temporal_context` | 临床安全语义链路提供的时间上下文 |

`slots` 是兼容视图，不是硬槽位状态机。后续模块不应把 `slots` 的缺失直接等价为“必须追问”，也不应绕过证据画像和 OPA 策略直接根据某个槽位生成回答充分性结论。

## 5. 状态存储边界

活跃问诊状态由 PostgreSQL `consultation_states` 表承载。生产业务层只能通过问诊状态仓储和记忆服务门面读写状态，不应直接访问 SQLAlchemy 表模型。

当前存储语义：

| 维度 | 语义 |
|---|---|
| `user_id` | 可信用户范围 |
| `pet_id` | 可信宠物范围 |
| `session_id` | 可信会话范围 |
| `task_key` | 当前任务状态键，`__default__` 表示默认单任务状态 |
| `state` | 结构化活跃问诊状态 JSON |
| `version` | 状态更新版本 |

单任务场景：

1. 未完成时保存到 `task_key=__default__`。
2. 完成回答后清理默认活跃状态。
3. 后续新主诉不应被已完成状态污染。

多任务场景：

1. 每个任务按任务路由给出的稳定 `task_key` 独立保存状态。
2. 已完成任务从多任务状态集合中移除。
3. 未完成任务继续保存，后续输入可通过任务路由承接既有任务。
4. 旧默认状态迁移到具体任务键时，可以在同一次写入中清理 `__default__`，避免双可信源。

删除治理：

1. 宠物范围删除应同时清理活跃问诊状态。
2. 活跃问诊状态删除不代表长期权威事实删除。
3. Mem0 语义投影删除由记忆治理链路负责，不由问诊状态层直接执行。

## 6. 配置与策略边界

当前与本阶段直接相关的运行配置包括：

| 配置项 | 语义 |
|---|---|
| `CONSULTATION_ANSWERABILITY_OPA_BASE_URL` | 回答充分性 OPA Data API 基地址 |
| `CONSULTATION_ANSWERABILITY_OPA_PACKAGE_PATH` | OPA package 路径，默认 `vet_agent.consultation_state` |
| `CONSULTATION_ANSWERABILITY_OPA_RULE_NAME` | OPA 规则名，默认 `decision` |
| `CONSULTATION_ANSWERABILITY_OPA_AUTH_TOKEN` | 可选 OPA Bearer 令牌 |
| `CONSULTATION_MAX_FOLLOWUP_ROUNDS` | 同一任务最大连续追问轮数 |
| `turn_options.max_followup_questions` | 单次 API 请求允许的最大追问问题数 |

配置边界：

1. 生产主路径应使用 OPA 回答充分性策略客户端。
2. 本地策略客户端仅供显式测试注入，不作为生产隐式降级。
3. OPA 策略缺失、响应字段缺失或响应类型非法必须 Fail Fast。
4. 目录配置只表达问诊域与槽位展示/追问文案，不承载关键词、正则或抽取规则。
5. 不应通过环境变量新增隐藏状态机开关。

## 7. 真实服务测试边界

本阶段新增真实服务集成 API 测试，用于验证“当前代码 + 当前 OPA 策略 + 真实 PostgreSQL + 真实 LiteLLM”的纵向链路。

测试定位：

1. 默认不进入普通单元门禁。
2. 需要显式开启 `RUN_CONSULTATION_STATE_API_EXTERNAL_TEST=true`。
3. 推荐通过 `scripts/integration/run-consultation-state-api-smoke.sh` 启动。
4. 默认通过 SSH 隧道访问远程开发依赖，降低公网直连不稳定对测试的影响。
5. 测试前可将当前分支中的问诊回答充分性 Rego 策略同步到测试 OPA。
6. Mem0 可通过显式开关纳入测试，但问诊状态自身不依赖 Mem0 存储。

覆盖范围：

| 覆盖项 | 说明 |
|---|---|
| 依赖可达性 | PostgreSQL、LiteLLM 模型列表、LiteLLM embedding、OPA Data API |
| 追问路径 | 首轮信息不足时返回 `requires_followup`，且不调用最终回答生成 |
| 回答路径 | 用户要求先答或证据足够时返回 `completed` |
| 策略审计 | metadata 中可观察 OPA 回答充分性策略路径 |
| 记忆读取 | 可观察 PostgreSQL 权威记忆与可选 Mem0 投影状态 |
| Agent 路径 | 可观察 `ConsultationStateService` 与 `ConsultationAnswerabilityPolicyOPA` |

测试不覆盖：

1. 生产发布部署流程。
2. 管理后台目录治理。
3. 大规模并发性能。
4. 医学内容正确性评估。
5. LlamaIndex RAG 迁移后的最终检索效果。
6. 长期记忆写入策略和删除纠正治理。

## 8. Fail Fast 语义

本阶段坚持以下 Fail Fast 边界：

1. OPA 回答充分性策略不可用时，本轮不应隐式降级为本地规则。
2. OPA 返回缺少 `result` 或缺少必需字段时，本轮不应被默认为允许回答。
3. `ask` 裁决没有可追问槽位时，应按契约错误失败。
4. `ask` 裁决无法生成追问问题时，应按契约错误失败。
5. 问诊领域或槽位目录不可用时，不应回退到硬编码关键词问诊状态机。
6. 问诊语义低置信或失败时，不应通过本阶段补造事实。

这些失败应暴露为依赖错误或契约错误，供 API 层、CI、真实服务 try-run 和运维排障定位，而不是被“尽量回答”吞掉。

## 9. 防退化约束

后续阶段实现时，应继续避免以下退化方向。

### 9.1 避免自定义规则状态机退化

不应在问诊状态层引入如下逻辑：

1. 按固定 if/else 分支维护问诊阶段流转。
2. 按不同症状类别硬编码追问顺序。
3. 根据追问轮数之外的隐式变量改变回答准入。
4. 在 Rego 中实现复杂多轮状态机。
5. 使用配置项隐藏业务状态机。

允许保留的确定性逻辑仅限技术不变量，例如状态归一、结构化字段合并、去重、体积限制、策略输入构造和策略响应契约校验。

### 9.2 避免硬槽位匹配退化

不应将某个固定槽位缺失直接等价为“不能回答”。判断应优先经由证据画像和 OPA 策略完成。

允许存在的槽位目录只用于：

1. 表达当前问诊域建议关注的信息类型。
2. 提供用户可理解的追问标签和默认追问文案。
3. 为追问规划提供结构化候选。

槽位目录不应用于：

1. 文本抽取。
2. 疾病分类。
3. 临床安全动作。
4. 长期事实写入。
5. 策略层自然语言扫描。

### 9.3 避免硬关键词匹配退化

不应在本阶段重新引入：

1. 用户原文关键词扫描。
2. 正则补槽。
3. seed 示例句匹配。
4. 问题模板反推事实。
5. 基于文本包含关系的回答充分性判断。

需要理解自然语言时，应由上游问诊语义抽取阶段通过 LiteLLM `response_format` 与 Pydantic 契约完成；本阶段只消费结构化结果。

## 10. 与相邻阶段的对齐

### 10.1 与问诊语义抽取对齐

问诊语义抽取是核心事实、开放观察和用户意图的主来源。问诊状态阶段只合并可信结构化结果，不解析模型原文。

如需新增核心事实键，应同步评审：

1. 问诊语义输出契约。
2. 问诊领域/槽位目录。
3. 状态合并语义。
4. 证据画像投影。
5. OPA 策略测试。
6. 响应 metadata 兼容性。

### 10.2 与多任务拆分对齐

多任务拆分负责确定任务边界和任务键。问诊状态阶段必须按任务键隔离状态，不应在多个任务之间共享未完成槽位、工作事实或追问轮数。

### 10.3 与记忆读取对齐

记忆读取负责提供权威事实、会话摘要、episode 和可选 Mem0 语义投影。问诊状态可读取活跃状态，但不应把 Mem0 语义记忆当作活跃状态来源。

### 10.4 与临床安全对齐

临床安全链路负责急诊、阻断、升级和安全动作。问诊状态阶段可以消费时间语义摘要，但不得根据问诊状态直接替代临床安全裁决。

阶段 3 后，临床安全前提评估还可向问诊状态提供单一结构化信号：
`clinical_safety_precondition_unknown`。当该信号为真且未达到追问上限时，
问诊状态将 `symptom_detail` 置为最高优先级追问槽位，回答充分性策略输出
`clinical_safety_precondition_unknown` 模式。问诊状态只消费该结构化信息缺口，
不解析候选资产、不读取自然语言前提、不生成临床安全动作。

### 10.5 与 RAG 追问和回答生成对齐

RAG 追问规划只在 OPA 裁决为 `ask` 后执行；回答 RAG 和最终回复生成只在 OPA 裁决为 `answer` 后执行。RAG 结果不得反向改变回答充分性裁决。

### 10.6 与长期记忆写入对齐

活跃问诊状态是当前 session/task 工作记忆，不是长期权威事实。长期事实写入必须经后续记忆候选抽取、写入策略和权威事实仓储完成。

## 12. 后续实现约束

后续模块接入本阶段结果时，应遵守以下约束：

1. 只依赖公开响应字段、仓储协议和包级导出，不跨包直接引用内部实现。
2. 需要判断回答充分性时，只消费 `answerability` 结果，不重新按槽位缺失自行裁决。
3. 需要生成追问时，只消费 `missing_slots`、`followup_question_plan` 和知识证据，不改写问诊状态。
4. 需要生成最终回答时，必须确认当前任务已经进入 `ready_to_answer` 或 `answerability.decision=answer`。
5. 需要写入长期记忆时，应走长期记忆候选和写入策略，不直接保存 `consultation_state`。
6. 需要做真实服务验收时，应使用显式 integration 开关和 SSH 隧道脚本，不把外部依赖测试混入普通单元门禁。
7. 需要新增配置时，应优先确认是否属于目录治理、策略治理或后续领域；避免在本阶段新增悬空配置项。

## 13. 验收基线

本阶段完成后，后续变更至少应保持以下验收语义：

1. 单任务首轮信息不足时返回 `requires_followup`，不调用最终回答生成。
2. 用户明确要求先答且具备最低上下文时返回 `completed`，并进入阶段性回答。
3. 多任务中每个任务独立保存或清理状态。
4. 已完成状态不会污染下一次新主诉。
5. 宠物可信画像只预填稳定身份事实，未验证 `pet_info` 不得独立驱动临床判断。
6. OPA 策略缺失或响应契约非法时必须 Fail Fast。
7. 默认测试不依赖真实外部服务；真实服务测试必须通过显式开关启用。
8. 响应 metadata 能审计问诊语义、问诊状态、回答充分性策略、追问规划和 Agent 路径。

若后续阶段需要改变上述语义，应先更新迁移方案、本文档、单元测试、OPA 策略测试和真实服务集成测试。
