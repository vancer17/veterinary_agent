# 可持久化后台任务变更总结

> **文档状态**：迁移完成后的对齐基线
>
> **适用范围**：主回合后置任务入队、后台 worker、任务身份与顺序约束、长期记忆候选抽取异步执行、任务重试与死信审计
>
> **不适用范围**：长期事实写入 OPA 治理、删除与纠正治理、Mem0 投影重构、任务管理后台和外部队列替换

## 1. 变更目的

本次迁移将主回合结束后的长期记忆候选抽取从同步执行改为持久化后台任务。

迁移后，主回合只负责：

1. 完成输出安全复核。
2. 构造 `memory_extraction_sources`。
3. 写入 `memory_candidate_extraction` 后台任务。
4. 在响应 metadata 中返回任务摘要。

后台 worker 负责：

1. 领取可执行任务。
2. 重建长期记忆候选抽取上下文。
3. 调用结构化抽取器。
4. 将抽取结果写入任务结果审计。
5. 持久化任务成功、重试或死信状态。

本次迁移只建立“可持久化后台任务底座”。它不把任务系统升级为业务事实库，也不把任务处理器变成跨领域治理中心。

## 2. 稳定边界

### 2.1 主回合边界

主回合不再同步等待 `MemoryExtractionAgent.extract` 完成，也不再在 `VetOrchestrator` 中直接调用 `upsert_pet_fact`。

主回合响应中的 `metadata.memory_extraction` 表示“任务已入队或被显式跳过”，不表示候选已经抽取完成或事实已经写入。

### 2.2 后台任务边界

后台任务状态由 PostgreSQL `background_tasks` 表承载。

当前稳定任务类型为：

| 任务类型 | 说明 |
|---|---|
| `memory_candidate_extraction` | 长期记忆候选抽取，不执行权威事实写入 |
| `mem0_turn_projection` | TODO 占位，后续交由中期 episode 与语义记忆投影阶段实现 |
| `TODO` | 显式占位任务类型，不应在生产主路径入队 |

后台任务状态包括：

| 状态 | 说明 |
|---|---|
| `pending` | 已入队，等待执行 |
| `running` | 已由 worker 领取并持有租约 |
| `retrying` | 执行失败，等待下一次重试 |
| `succeeded` | 执行成功 |
| `dead_letter` | 达到不可恢复失败或超过重试边界 |
| `cancelled` | 已取消 |

### 2.3 任务身份与顺序边界

每个后台任务必须具备稳定身份和可审计来源。

| 字段 | 稳定语义 |
|---|---|
| `task_type` | 任务类型，用于选择处理器和治理边界 |
| `business_key` | 业务幂等键，同一任务类型下用于去重或恢复入队 |
| `ordering_key` | 顺序约束键，用于限制同一业务时间线内的并发执行 |
| `source_turn_id` | 来源回合标识，用于回溯主回合响应 |
| `source_request_id` | 来源请求标识，用于排查请求链路 |
| `source_trace_id` | 来源追踪标识，用于关联 trace 和日志 |

`business_key` 解决重复入队问题，`ordering_key` 解决同一时间线内的并发顺序问题。二者不可互相替代。

当前长期记忆候选抽取使用用户、宠物、会话范围构造顺序约束，避免同一会话下的多条后置任务并发污染时间语义。不同 `ordering_key` 的任务可以并行执行，但任务结果仍不得绕过后续治理直接成为业务事实。

### 2.4 任务结果边界

后台任务结果只表达“任务执行审计”，不表达最终业务真相。

当前 `memory_candidate_extraction` 的任务结果可以包含候选数量、候选键、结构化候选摘要、错误类型和失败原因，但这些信息不表示：

1. 候选已经写入权威长期事实库。
2. 候选已经完成冲突、覆盖、删除或纠正治理。
3. 候选已经同步到 Mem0。
4. 候选已经通过用户确认或人工确认。

后续模块可以消费任务结果作为输入，但必须在各自职责组件内重新形成权威状态和审计记录。

### 2.5 容器运行边界

正式环境和开发环境均提供独立 `worker` 服务。

`app` 与 `worker` 复用同一个预编译应用镜像，通过启动命令区分运行角色：

| 服务 | 运行职责 |
|---|---|
| `app` | 处理 HTTP 请求、完成主回合响应、写入后台任务 |
| `worker` | 领取 `background_tasks` 中的待执行任务并推进任务状态 |

生产环境不得为 worker 现场构建独立镜像，也不得维护第二套 worker 代码包。CD 在迁移完成后同时拉起 `app` 与 `worker`，并通过 Compose healthcheck 校验 worker 能访问后台任务仓储。

worker 容器的健康检查只验证 `DATABASE_URL` 与后台任务表可访问性。LiteLLM、OPA、Mem0 等业务依赖异常应由具体任务进入重试或死信审计，不应作为容器存活判断的唯一依据。

## 3. 兼容接口

### 3.1 主回合响应兼容

主回合继续保留 `metadata.memory_extraction` 字段，但语义发生变化：

| 字段 | 语义 |
|---|---|
| `strategy` | `background_task_queued`、`background_task_disabled` 或原有 skipped 状态 |
| `task_id` | 已入队后台任务标识；未入队时为空 |
| `task_status` | 当前任务初始状态或跳过状态 |
| `task` | 后台任务轻量摘要 |
| `proposal_count` | 主回合返回时固定为 0，真实候选数量在任务结果中记录 |
| `stored_fact_count` | 主回合返回时固定为 0，真实写入数量在任务结果中记录 |

调用方不应把主响应中的 `proposal_count=0` 理解为“本轮没有长期记忆候选”，它只表示后台任务尚未执行。

当前 `memory_candidate_extraction` 任务结果中的 `stored_fact_count` 固定为 0，并通过 `fact_write_status=TODO` 显式表明长期事实写入治理尚未接入。任何调用方都不应从后台任务结果直接推断权威事实已经落库。

### 3.2 后台任务摘要兼容

主回合响应、日志和后续治理可以读取后台任务轻量摘要。

| 字段 | 语义 |
|---|---|
| `task_id` | 后台任务稳定标识 |
| `task_type` | 后台任务类型 |
| `business_key` | 任务幂等键 |
| `ordering_key` | 任务顺序约束键 |
| `status` | 当前任务状态 |
| `attempt_count` | 已尝试执行次数 |
| `max_attempts` | 最大允许尝试次数 |
| `source_turn_id` | 来源回合标识 |
| `source_request_id` | 来源请求标识 |
| `source_trace_id` | 来源追踪标识 |

该摘要用于审计和排障，不应包含敏感密钥、完整提示词、外部服务响应原文或大体积业务载荷。

### 3.3 运行配置兼容

后台任务底座当前稳定配置如下：

| 配置 | 语义 |
|---|---|
| `BACKGROUND_TASKS_MAX_ATTEMPTS` | 单条任务最大尝试次数 |
| `BACKGROUND_TASKS_WORKER_BATCH_SIZE` | Worker 单轮领取任务数量 |
| `BACKGROUND_TASKS_WORKER_LEASE_SECONDS` | 任务租约时长 |
| `BACKGROUND_TASKS_WORKER_POLL_INTERVAL_SECONDS` | Worker 空轮询间隔 |

这些配置只影响任务执行节奏和故障恢复窗口，不改变业务语义。敏感信息仍由各业务依赖的 env 配置承载，非敏感服务参数后续可继续向 `application.yml` 收敛。

### 3.4 包出口兼容

后台任务领域通过 `vet_agent.background_tasks` 与 `vet_agent.repositories` 的包顶层出口向外暴露稳定能力。

后续模块不得直接跨包引用后台任务内部实现文件，也不得绕过仓储直接操作 SQLAlchemy 数据表。需要入队、领取、完成、重试或死信标记时，应通过后台任务服务或仓储契约完成。

## 4. 有意 TODO

以下事项有意不在本阶段实现：

| TODO | 边界说明 |
|---|---|
| 长期事实写入 OPA 治理 | 当前仅迁移任务持久化与候选抽取；正式写入裁决后续独立实现 |
| 删除与纠正治理 | 冲突、覆盖、失效和修正不在后台任务基础设施层判断 |
| Mem0 投影后台化 | 已保留任务类型占位，后续由中期 episode 与语义记忆投影阶段接管 |
| 任务管理后台 | 当前仅提供数据库状态，不新增管理 API |
| 死信任务运维流程 | 当前仅记录 dead letter 状态，不实现人工重放、批量取消或管理后台 |
| 任务结果物化治理 | 当前任务结果只保存执行审计，不新增跨任务的候选事实物化表 |
| 任务清理与归档 | 当前不实现历史任务 TTL、归档和压缩策略 |
| Worker 自动扩缩容策略 | 当前只提供可横向运行的 worker 容器，不内置容量调度策略 |
| 外部队列 | 当前 PostgreSQL 是唯一任务可信源，不引入 Redis、Celery 或消息队列作为主状态 |

## 5. 后续对齐原则

后续新增后台任务时应遵守以下原则：

1. 任务必须有稳定 `task_type` 与 `business_key`。
2. 同一业务语义重复入队必须幂等。
3. 任务载荷必须足够 worker 独立重建上下文。
4. 任务失败必须进入 retry 或 dead letter，不允许静默吞异常。
5. 业务事实状态不得只保存在任务表结果中。
6. 跨领域治理不得通过后台任务处理器临时扩展为隐藏状态机。
7. 同一 `ordering_key` 下的任务不得依赖无约束并发执行来表达时间语义。
8. 任务载荷应保存重建上下文所需的最小结构化信息，不应保存敏感密钥或大体积外部响应。
9. 新增任务类型必须先明确所属职责组件，不能把后台任务底座当作业务策略兜底层。

## 6. 与后续模块的关系

可持久化后台任务与以下模块存在协作关系，但不共享职责：

| 模块 | 关系 |
|---|---|
| `长期记忆候选抽取` | 当前首个接入后台任务的业务任务，负责异步候选抽取 |
| `长期事实写入治理` | 后续可消费候选结果，但必须独立形成写入裁决和权威事实 |
| `删除与纠正治理` | 后续可通过任务底座执行异步治理动作，但冲突语义不在任务底座判断 |
| `中期 episode 与语义记忆投影` | 后续可复用任务底座执行 Mem0 投影或重放 |
| `运维后台` | 后续可读取任务状态、重试和死信记录，但当前阶段不提供管理 API |

## 7. 结论

可持久化后台任务现在是主回合后置副作用的执行底座。

长期记忆候选抽取已经从主链路同步执行迁移到后台任务；后续长期事实写入治理、删除与纠正治理、Mem0 语义投影应继续复用该任务底座，但不应把各自业务策略塞回 `VetOrchestrator`，也不应把任务结果直接提升为业务事实可信源。
