# 临床安全补齐测试基线变更总结

> **文档状态**：阶段 0 迁移后的对齐基线；不表示临床安全职责边界已经最终收束
>
> **适用范围**：临床安全回归测试、结构化证据边界、候选召回输入边界、OPA required_context 消费、响应主信号投影、资产 code 治理防退化门禁
>
> **不适用范围**：完整医学资产治理后台、完整风险证据字段产品化、症状标准化词表、完整急诊 code 拆分、生产外部依赖压测、长期记忆和 RAG 医学问答
>
> **职责漂移状态**：已消除最危险的旧回退与默认编码路径；仍保留若干阶段性过渡边界，后续阶段必须继续收束。

## 1. 变更目的

本次迁移的目标是把 `docs/architecture/clinical-safety-open-issues-migration-plan.md` 中“补齐测试基线”部分落成可回归、可定位、可继续扩展的工程基线。

迁移前，临床安全链路存在以下残余风险：

1. 用户只是提出 `triage` 分诊意图时，容易被误解为已经存在急诊风险事实。
2. 宠物画像、年龄和模糊主诉被共同拼入召回正文后，可能放大为泛化 urgent 候选。
3. 资产中已声明的 `required_context` 没有完整进入策略输入和结构化裁决面。
4. 多个 urgent 候选会在用户响应层被批量拼接，形成互不相关的急诊建议。
5. 离线资产转换器仍可能使用序号型默认 code 掩盖资产治理缺口。
6. 测试若继续依赖开发样例 JSON 或不稳定静态资产，会把参考数据误当成可信生产契约。

迁移后，阶段 0 的基线只做一件事：把上述边界变成稳定测试和最小运行时保护，防止后续阶段继续在旧路径上叠加逻辑。

需要明确的是，本次迁移不是最终架构重构完成标志。它只先建立可回归的安全边界，并将已确认的职责漂移显性化，后续阶段仍需继续把过渡判断迁移到更清晰的结构化契约和策略面。

## 2. 本次稳定边界

### 2.1 风险证据与分诊意图分离

本次迁移明确区分：

| 概念 | 含义 | 是否足以触发强临床安全召回 |
|---|---|---|
| `intent_type=triage` | 用户希望判断是否需要就医 | 否 |
| 明确暴露 | 用户表达误食、接触、可能接触风险物 | 是 |
| 明确症状 | 用户表达当前存在症状或异常表现 | 是 |
| 正向高风险线索 | 结构化语义抽取出的正向风险短语 | 是 |
| `symptom_state=unknown` 且 `exposure_state=unknown` | 本轮缺少可裁决风险事实 | 否 |

该边界不是新的医学规则状态机。它只定义“是否具备足够证据进入强安全召回和升级裁决”，不定义具体疾病、诊断、治疗方案或 code 分支。

### 2.2 宠物画像不再作为强召回正文

宠物画像仍是可信上下文，但本次基线将其从“embedding 主文本”中收缩出来。

当前约定：

1. 用户原文仍可作为召回主文本。
2. 结构化语义只有在存在正向风险证据时才可增强召回。
3. 宠物画像、年龄文本和性别信息不再无条件拼入强召回正文。
4. 物种、年龄和性别应优先作为结构化过滤或策略裁决上下文，而不是当前风险证据。

这保证“成年犬、雌性、3 岁”等画像信息不会在模糊分诊请求中单独放大为 urgent 资产候选。

### 2.3 `required_context` 进入策略输入

`required_context` 从资产文档字段进入 OPA 候选输入。

当前约定：

1. 候选 payload 可携带 `required_context`。
2. OPA 可以根据结构化语义判断候选前置上下文是否满足。
3. 高召回分数不能替代缺失的前置上下文事实。
4. 前置上下文不满足时，候选可以进入审计原因，但不得生成有效升级信号。

`required_context` 仍是结构化候选前提，不是运行时关键词规则。OPA 不读取原始用户文本，也不从自然语言中自行抽取症状。

### 2.4 用户响应只投影主安全信号

本次基线将“策略候选集合”和“用户可见分诊文本”分离。

当前约定：

1. `safety_signals` 仍可保留全部策略返回信号，供审计和 metadata 使用。
2. 用户可见安全分诊文本只展示一个主信号。
3. 主信号之外的其他候选不得被简单字符串拼接到用户响应中。
4. 当前主信号选择以 `blocked` 优先于 `urgent` 为最低稳定规则。

这不是完整的信号排序策略。后续仍需要在策略或响应投影域补充更明确的 tie-break 契约。

### 2.5 离线资产 code 必须显式声明

离线转换器不再根据资产类型、条目序号或医学名称生成默认 code。

当前约定：

1. 原始资产条目必须显式提供稳定 `code`。
2. 缺少 `code` 时转换阶段直接失败。
3. 发布态契约拒绝旧版序号型默认 code。
4. `code` 是资产身份，不是 Python 业务分支条件。

这意味着历史 `scripts/clinical_safety/assets/vet_safety_reference.json` 若未补齐显式 code，将不能直接作为发布源继续转换。该行为是有意设置的 Fail Fast 边界。

### 2.6 职责边界的阶段性收缩

本次迁移已经完成以下职责收缩：

1. 语义结果对象保持事实容器定位，不承载临床风险裁决职责。
2. Python 运行时不恢复旧版关键词规则或本地临床安全硬编码回退。
3. 候选是否满足 `required_context` 由 OPA 基于结构化输入裁决。
4. 用户响应层只做主信号投影，不重新生成候选或判断疾病模式。
5. 离线转换器不再通过默认 code 掩盖资产治理缺口。

以上收缩只覆盖阶段 0 所需的最小边界。后续阶段不得将这些边界解释为“可以继续在 evaluator、测试替身或响应层扩展临床判断逻辑”。

## 3. 兼容接口

### 3.1 对外 API 请求兼容

本次迁移不要求调用方新增请求字段。

以下入口保持兼容：

| 接口 | 兼容状态 | 说明 |
|---|---|---|
| `POST /agent/turns` | 保持兼容 | 请求字段不变 |
| `POST /openai/v1/responses` | 保持兼容 | 仍复用主业务临床安全链路 |

以下请求字段保持原有语义：

| 字段 | 兼容说明 |
|---|---|
| `input` | 仍是用户本轮输入；可进入语义抽取和召回主文本 |
| `scope_assertion.profile` | 仍是可信宠物画像来源 |
| `vet_context.pet_info` | 仍是兼容字段；不得覆盖可信画像形成硬裁决 |
| `metadata` | 仍只作为审计或透传信息，不作为临床规则来源 |
| `turn_options` | 幂等和流式相关语义不变 |
| `attachments` | 仍由输入安全和其他领域处理，临床安全基线不解析附件 |

### 3.2 响应接口兼容

本次迁移保持响应主结构兼容。

| 字段 | 兼容状态 | 说明 |
|---|---|---|
| `status` | 保持兼容 | 仍可返回 `completed`、`requires_followup`、`safety_escalated`、`blocked` |
| `output_text` | 语义收敛 | 安全升级时只投影主安全信号 |
| `safety_signals` | 保持兼容 | 可保留全部策略安全信号 |
| `metadata.clinical_safety_semantic` | 保持兼容 | 继续承载结构化语义审计 |
| `metadata.clinical_safety_resolution` | 保持兼容 | 继续承载临床安全裁决和降级状态 |
| `metadata.multi_agent_path` | 保持兼容 | 继续用于链路审计 |

调用方不应依赖安全升级文本中出现全部候选消息。后续应以 `safety_signals` 和 metadata 作为候选审计来源，以 `output_text` 作为用户可读主分诊信息。

### 3.3 OPA 输入契约兼容

OPA 临床安全输入新增或强化了候选 `required_context` 字段。

当前兼容策略：

1. 缺少 `required_context` 的旧候选仍可被解析为空前置条件。
2. 存在 `required_context` 时必须按结构化语义判断是否满足。
3. OPA 输入仍不包含用户原始全文。
4. OPA 仍不负责候选生成、自然语言解析或医学诊断。

后续如引入 `observed_features`、`risk_evidence_state` 或更完整的结构化事实字段，应保持向后兼容：新增字段可选，旧字段语义不反转。

### 3.4 资产治理接口的有意不兼容

离线资产源格式存在有意不兼容：

| 变更 | 影响 | 原因 |
|---|---|---|
| 原始资产缺少 `code` 时失败 | 旧参考 JSON 可能无法直接转换 | 防止序号型默认 code 进入发布链路 |
| 发布态拒绝序号型 code | 旧转换产物可能无法发布 | 防止资产身份与数组顺序绑定 |
| 测试不再依赖完整静态参考资产 | 旧资产内容变更不会影响默认单测 | 避免把不稳定参考资产作为 CI 可信源 |

这是本次迁移中唯一明确的兼容破坏点，且仅限离线资产治理输入，不影响线上 API 调用方。

## 4. 测试基线边界

### 4.1 默认门禁覆盖

默认 Python 测试和 OPA 测试覆盖以下基线：

1. `triage` 意图但症状和暴露未知时，不直接升级。
2. 模糊主诉不会仅因宠物画像进入强召回。
3. `required_context` 会进入 OPA 候选 payload。
4. `required_context` 不满足时候选不升级。
5. 多个 urgent 候选不会全部拼接到用户响应。
6. 离线转换器缺少显式 code 时快速失败。
7. 发布态资产拒绝旧版序号型默认 code。
8. 临床安全运行时代码不引用旧版 `safety_rules` 或 `SafetyAgent.analyze`。
9. OPA payload 不携带未结构化处理的用户原文。

这些测试表达的是架构边界，不表达完整医学知识覆盖率。

### 4.2 不再作为默认测试可信源的内容

以下内容不再作为默认测试基线：

1. 开发样例 JSON。
2. 仓库内不稳定临床安全参考资产全文。
3. 静态 seed 或历史规则文件。
4. 真实模型服务返回的自然语言文本。
5. 向量库中生产资产的实际排序。

需要真实服务验证时，应使用显式开启的 integration 测试，并写入隔离的最小测试资产。

### 4.3 防退化测试的范围

防退化测试只扫描有限生产路径：

1. `src/vet_agent/clinical_safety/`
2. `src/vet_agent/orchestrator.py`
3. `scripts/clinical_safety/converter.py`

防退化测试不扫描：

1. 文档。
2. 医学参考资产正文。
3. 开发样例。
4. vendor 子模块。
5. 历史迁移说明。

该范围是有意设置的，避免把“文档中描述禁止事项”或“医学资料中的关键词”误判为运行时规则。

## 5. Fail Fast 边界

本次迁移强化以下 Fail Fast 行为：

| 场景 | 当前行为 | 说明 |
|---|---|---|
| 原始资产缺少 `code` | 转换失败 | 不生成默认 code |
| 发布态 code 命中旧版默认编码模式 | 校验失败 | 不允许进入发布链路 |
| OPA 返回非法结构 | 策略客户端失败 | 不启用本地硬编码策略 |
| 语义无正向风险证据 | 不执行强召回 | 不把 triage 意图当作风险事实 |
| `required_context` 不满足 | 候选不升级 | 高分召回不能替代前置事实 |

需要注意：

1. “无候选”不是系统故障。
2. “语义未知”不是安全升级证据。
3. “服务不可用”不应被旧规则静默兜底。
4. “资产缺字段”不应由转换器或导入器自动补齐。

## 6. 有意保留的 TODO

本节列出的 TODO 均为有意保留的阶段性缺口。后续实现应替代当前过渡边界，而不是在其上继续累加业务规则。

### 6.1 显式 `risk_evidence_state`

本节原为阶段 0 的后续 TODO，现已由阶段 1 迁移完成。具体契约和运行时行为以
`docs/architecture/clinical-safety-evidence-boundary-change-summary.md` 为准。

阶段 1 已完成：

1. 在临床安全语义契约中引入显式 `risk_evidence_state`。
2. 将取值控制在 `sufficient`、`insufficient`、`unknown` 等有限枚举。
3. 由语义抽取层产出，由 OPA 消费。
4. 移除 evaluator 侧旧字段组合强召回门槛。
5. 语义未知时不启用候选高分或关键词回退。

当前残留状态：`observed_features` 和复杂 `required_context` 满足语义仍属于后续阶段，不在本次迁移范围内。

### 6.2 结构化 `observed_features`

当前 `required_context.symptoms` 的满足性主要依赖结构化高风险线索集合，仍不是完整的症状标准化体系。

后续建议：

1. 引入受控的 `observed_features` 或同等结构化事实集合。
2. 由语义抽取层或专门临床事实抽取层产出。
3. 在 OPA 中进行集合满足判断。
4. 不在 OPA 或 Python 业务层扫描原始文本。

当前残留状态：`required_context.symptoms` 的满足性仍缺少稳定的结构化症状事实来源。后续不应把症状匹配补成关键词表，而应先定义可审计的事实字段，再由 OPA 做集合关系判断。

### 6.3 `required_context` 满足策略细化

当前 `required_context` 已进入裁决面，但满足逻辑仍保持保守。

后续建议：

1. 支持 `all_of`、`any_of` 或受控组合语义。
2. 明确物种、年龄、性别和症状字段的缺省含义。
3. 将“不匹配”“未知”“未提供”“明确否认”区分为不同审计原因。
4. 避免将 required_context 设计成自由格式 DSL。

当前残留状态：`required_context` 已进入裁决面，但组合语义和未知值处理仍是保守基线。后续应扩展契约，而不是让 Python 业务层按资产 code 或症状名称补分支。

### 6.4 急诊 code 拆分

本次只阻止序号型默认 code 和用户响应多候选拼接，尚未完成全部急诊模式 code 治理。

后续建议：

1. 将历史泛化 `EMERGENCY_RED_FLAG` 拆分为具体稳定 code。
2. 将 `asset_type`、`category`、`action_class` 与 `code` 的职责分离。
3. 不在 Python 中按 `candidate.code` 编写医学 if/else。
4. 将候选优先级交给策略或统一投影器，而不是散落在响应字符串拼接中。

### 6.5 主信号排序契约

当前用户响应只展示一个主信号，并以 `blocked` 优先于 `urgent` 为最低稳定规则。

后续建议：

1. 定义同级信号排序策略。
2. 明确毒物、当前生命体征、时间持续性、证据充分性和候选分数之间的优先级关系。
3. 将主信号和次级候选分别写入 metadata。
4. 保持用户文本简洁，避免重新出现批量拼接。

当前残留状态：主信号投影只有最低稳定优先级，尚未形成完整排序契约。后续应由策略或统一投影契约给出可审计排序依据，响应层只消费结果。

### 6.6 真实服务集成基线

当前默认门禁不依赖真实模型、真实向量库或生产资产。

后续建议：

1. 在显式开启的 integration job 中写入隔离测试资产。
2. 验证真实 LiteLLM 语义、pgvector 召回和 OPA 裁决闭环。
3. 不使用开发样例 JSON 或生产资产排序作为断言依据。
4. 在预发布环境增加模糊分诊、required_context 不满足、多候选投影等冒烟用例。

### 6.7 资产治理源文件补齐

历史 `scripts/clinical_safety/assets/vet_safety_reference.json` 当前只是参考资产，不再适合作为默认发布源。

后续建议：

1. 为可发布资产补齐显式稳定 code。
2. 将参考资产与发布资产分离。
3. 对发布资产引入医学审核记录和版本管理。
4. 将资产发布流程纳入独立治理，而不是依赖转换器兜底。

### 6.8 召回正文与策略上下文拆分

当前召回输入已经阻止无证据场景下的宠物画像污染，但召回增强文本与结构化策略上下文尚未彻底拆分。

后续建议：

1. 将 embedding 主文本限定为用户明确表达的召回事实片段。
2. 将物种、性别、年龄、意图、时间状态等上下文固定放入策略输入。
3. 明确哪些字段允许作为弱召回增强，哪些字段只能用于过滤或裁决。
4. 不把宠物画像重新作为强召回正文。

当前残留状态：语义对象仍暴露召回提示文本生成能力，其中包含部分画像和状态字段。该能力应在后续阶段拆为更明确的召回输入契约与策略 payload 契约。

### 6.9 测试替身策略收缩

当前 API 测试仍存在少量测试策略替身，用于验证主链路响应投影和 metadata 串联。

后续建议：

1. API 测试替身只返回预设策略结果，不复制 OPA 的业务判断。
2. 生产策略行为由 OPA Rego 测试和显式 integration 测试覆盖。
3. 避免测试替身逐步增长为第二套临床安全策略。
4. 对必须保留的测试替身标注其只服务测试链路，不作为生产回退。

当前残留状态：测试替身中仍有少量上下文过滤逻辑。该逻辑不进入生产路径，但后续应继续压缩，降低维护者把测试替身误认为策略权威的风险。

## 7. 残留职责漂移清单

以下问题在阶段 0 后仍未完全收束，后续阶段实现时必须显式处理：

| 残留项 | 当前状态 | 后续收束方向 |
|---|---|---|
| 召回提示与策略上下文混合 | 语义层仍能生成包含画像和状态字段的查询提示 | 拆分召回事实文本与策略上下文 payload |
| `required_context.symptoms` 缺少正式事实源 | 当前只能基于既有结构化线索做保守满足判断 | 引入 `observed_features` 或等价事实集合 |
| 主信号排序契约不完整 | 响应层只实现最低限度主信号投影 | 将排序依据产品化为策略输出或统一投影契约 |
| API 测试替身仍有少量策略逻辑 | 仅用于测试，但存在复制策略的趋势 | 让测试替身只返回预置决策，真实策略行为交给 OPA 测试 |
| 急诊 code 治理未完全完成 | 已禁止默认 code，但未完成全部历史 code 拆分 | 在资产治理阶段补齐具体、稳定、可审计 code |

这些残留项不是阶段 0 的失败项，而是有意保留的后续迁移边界。任何后续实现如果扩大这些过渡逻辑，都应视为职责漂移风险。

## 8. 后续实现约束

后续阶段实现时，应遵循以下原则：

1. 不新增 Python 业务层 `candidate.code` 医学分支。
2. 不新增原始文本关键词到急诊结论的直接映射。
3. 不让 OPA 扫描原始用户文本。
4. 不把宠物画像重新作为强召回主正文。
5. 不把开发样例 JSON 或不稳定静态资产纳入默认 CI 可信源。
6. 不恢复序号型默认 code 生成。
7. 不在 OPA 不可用时启用本地临床安全硬编码策略。
8. 不把多个 urgent 候选直接拼接给用户。
9. 不把 `required_context` 继续停留在文档字段。
10. 不把测试夹具扩展为另一套隐式业务规则。
11. 不把阶段 0 的过渡门槛解释为长期策略权威。
12. 不重新引入 Python 侧字段组合、关键词或候选分数证据判断分支。

## 9. 阶段 0 完成判定

本阶段可以认为完成，当且仅当以下条件持续满足。该判定只表示“补齐测试基线”完成，不表示全部职责漂移已经完全收束。

1. 默认 Python 测试通过。
2. OPA 策略测试通过。
3. 防退化测试覆盖旧规则入口、默认 code 生成和 OPA 原文输入边界。
4. 模糊分诊请求不会仅因宠物画像触发 urgent 升级。
5. `required_context` 已进入 OPA 输入并影响候选有效性。
6. 用户响应只展示一个主安全信号。
7. 离线资产缺少显式 code 时快速失败。
8. 后续阶段实现可以基于本文档继续扩展，而不需要恢复旧版关键词回退路径。
