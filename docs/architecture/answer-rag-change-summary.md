# 回答相关 RAG 变更总结

> **文档状态**：迁移完成后的对齐基线
>
> **适用范围**：问诊回答充分性 `answer` 分支、回答相关证据召回、响应元数据、审计路径、真实服务联调
>
> **不适用范围**：回答充分性裁决、问诊状态流转、临床安全裁决、追问计划生成、长期记忆写入、自然语言回复策略、知识资产审核发布

## 1. 变更目的

回答相关 RAG 的迁移目标，是把“回答时应依赖什么证据”从旧版默认模板、关键词路径、文本相似度兜底、本地文件兜底和开发样例资产中收束出来，改为只依赖上游结构化结论和已治理知识资产。

迁移后的回答相关 RAG 只承担“证据供给”职责。它不决定本轮是否回答，不生成最终自然语言回复，也不在无命中时构造默认知识。

## 2. 作用边界

### 2.1 允许承担的职责

回答相关 RAG 允许承担以下职责：

1. 接收已经由上游裁决为 `answer` 的请求。
2. 消费服务端已验证的身份、宠物资料、会话范围和当前任务文本。
3. 消费上游问诊状态、回答充分性结论和问诊语义抽取结果。
4. 从已启用、已审核且具备向量的知识资产中召回答案证据。
5. 输出可进入回复生成链路的证据摘要和可观测 metadata。
6. 在依赖缺失、契约不符或无有效知识命中时显式失败。

### 2.2 明确不承担的职责

回答相关 RAG 不承担以下职责：

1. 不判断本轮应该回答还是继续追问。
2. 不修改问诊状态、会话状态、长期记忆或宠物资料。
3. 不执行临床安全裁决或输出安全复核。
4. 不生成最终自然语言回复。
5. 不审核、发布、修订或自动生产知识资产。
6. 不通过关键词、正则、默认模板或手写规则补齐回答证据。
7. 不把开发样例 JSON、seed 静态资产或未审核资产当作生产知识来源。

### 2.3 知识资产边界

回答相关 RAG 只使用当前正式知识资产承载层，不额外引入第二套生产知识源。

稳定知识约束如下：

| 约束 | 含义 |
|---|---|
| 启用状态 | 只允许使用已启用资产 |
| 审核状态 | 只允许使用已审核通过资产 |
| 向量可用性 | 只允许使用 embedding 非空资产 |
| 资产类型 | 只允许使用回答链路允许的 chunk 类型 |
| 来源边界 | 不使用开发样例、临时 seed、未治理静态文件或隐式默认知识 |

任务域、宠物资料和会话范围可以参与结构化检索语义，但不得退化为一组硬编码规则。

## 3. 兼容接口

### 3.1 主业务入口保持不变

回答相关 RAG 不对外新增独立业务请求入口。外部调用方仍通过既有入口触发 Agent 回合：

| 接口 | 兼容语义 |
|---|---|
| `POST /agent/turns` | 主业务入口；回答相关 RAG 在后端 `answer` 分支内部触发 |
| `POST /openai/v1/responses` | OpenAI 兼容入口；与主业务入口保持同一回答语义和失败语义 |

调用方不需要，也不应该通过新增字段、关键词或特殊提示词来强制触发回答相关 RAG。

### 3.2 稳定响应面

回答相关 RAG 对后续实现保持以下稳定响应面：

| 对齐项 | 语义 |
|---|---|
| `evidence` | 面向回复生成、审计和引用展示的证据列表 |
| `metadata.answer_rag` | 回答相关 RAG 的可观测摘要 |
| `metadata.multi_agent_path` | 回合执行路径中的回答 RAG 节点审计 |
| `reasoning_display` | 面向展示的受控推理摘要，不承载隐藏规则 |
| `trace_id` / `request_id` | 用于跨服务排障和治理回溯 |

后续可以扩展字段，但不应破坏上述字段的语义，也不应把临时调试信息伪装成稳定业务字段。

### 3.3 稳定失败面

以下情况必须保持显式失败：

1. 上游回答充分性结论不是 `answer`。
2. 当前用户任务文本为空或结构化输入不满足契约。
3. 关键配置缺失或非法。
4. embedding、数据库、向量检索或知识资产依赖不可用。
5. 没有已启用、已审核、具备向量且达到阈值的知识命中。

失败时不得返回空证据回答，不得构造默认 `AnswerRagResult`，不得继续进入自然语言回复生成。

## 4. 与 RAG 无命中治理的关系

回答相关 RAG 无命中时，运行时行为仍然是 Fail Fast；治理链路只负责把失败上下文记录为后续知识资产补充材料。

稳定约束如下：

1. 无命中记录不改变当前回合结果。
2. 无命中记录不生成知识、不生成 embedding、不自动发布 chunk。
3. 无命中记录用于后续人工确认、知识导入、审核发布和治理追踪。
4. 后台可以基于治理记录聚合同类缺口，但聚合结果不得回流为运行时硬编码规则。

这意味着“可治理”只解决知识缺口的可发现和可追踪问题，不解决当前回合的回答兜底问题。

## 5. 多任务与审计

回答相关 RAG 可以出现在多任务回合中，但必须只服务当前回答任务。

稳定约束如下：

1. 回答任务和追问任务各自维护证据与审计信息。
2. 一个任务的回答证据不得被另一个任务隐式复用。
3. 多任务响应应能通过 metadata 区分回答 RAG 是否参与、参与哪个任务、使用了哪些证据。
4. 审计信息应能说明本轮是否存在 RAG 无命中、依赖失败或无回退路径。

## 6. 不允许恢复的旧路径

以下路径已明确废弃，后续实现不得以兼容名义恢复：

1. 关键词回答路径。
2. 正则或手写规则回答路径。
3. 默认回答模板。
4. 默认知识命中。
5. 文本相似度兜底。
6. 本地文件知识兜底。
7. 开发样例 JSON 兜底。
8. seed 静态资产兜底。
9. 无命中时返回空结果继续生成回答。

如果确实需要补齐能力，应进入知识资产治理流程，而不是回到运行时规则路径。

## 7. 有意保留的 TODO

以下 TODO 是有意保留的后续建设项，不代表当前回答相关 RAG 实现缺失：

| TODO | 当前边界 |
|---|---|
| 回答知识质量评测集 | 当前只保证契约、审核状态和可追溯性；医学质量评测需单独建设 |
| 引用与出处展示细化 | 当前保证 `evidence` 与 `metadata.answer_rag` 稳定，不把展示策略写死在召回链路中 |
| RAG 无命中聚合视图 | 当前已具备治理记录与聚合键，后台聚合视图可后续扩展 |
| 知识导入批次自动关联 | 当前由治理记录保存关联字段，自动关联流程后续建设 |
| 多物种与多语言知识治理 | 当前以中文宠物问诊为主要范围，资产扩展不应影响主入口兼容 |
| 真实 PostgreSQL/pgvector 集成门禁 | 依赖 CI 环境提供数据库、embedding 和必要密钥后逐步纳入 |
| 回答知识发布工作流 | 当前不由回答 RAG 承担发布职责，应继续由知识治理链路承载 |
| 召回效果离线评测与回放 | 当前保留审计字段，离线评测与回放工具后续独立建设 |

这些 TODO 不应通过关键词规则、默认模板、开发样例资产或临时静态文件提前补齐。

## 8. 后续对齐原则

后续涉及回答相关 RAG 的变更，默认遵守以下原则：

1. 先保持主业务入口兼容，再扩展响应字段。
2. 先保持失败语义稳定，再优化召回效果。
3. 先进入知识治理链路补齐资产，再让正式 RAG 召回。
4. 可观测字段可以扩展，但不得承载隐式业务规则。
5. 任何无命中、依赖缺失或契约不符都应显式失败。
6. 回答相关 RAG 只做证据召回和上下文供给，不做上游裁决和最终回复生成。
