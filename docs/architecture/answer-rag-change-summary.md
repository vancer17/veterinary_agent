# 回答相关 RAG 变更总结

> **文档状态**：迁移完成后的对齐基线
>
> **适用范围**：问诊回答充分性 `answer` 分支、回答相关证据召回、响应元数据、审计路径、真实服务集成测试
>
> **不适用范围**：回答充分性裁决、问诊状态机、临床安全裁决、追问计划生成、长期记忆写入、自然语言回复策略

## 1. 变更目的

本次迁移的目标，是把“回答该依赖什么证据”从旧版默认模板、关键词路径、文本相似度回退和本地知识兜底中收束出来，改为由结构化回答充分性结果、已审核知识资产和受约束的证据召回共同驱动。

回答相关 RAG 只承担回答链路中的证据供给职责，不承担问诊状态编排职责，也不重新判断本轮是回答还是追问。

## 2. 作用边界

### 2.1 允许承担的职责

回答相关 RAG 允许做的事情只有以下几类：

1. 接收已经通过上游裁决的 `answer` 型请求。
2. 读取服务端已验证的会话范围、宠物上下文摘要和当前输入。
3. 从已启用且已审核的知识资产中召回回答证据。
4. 将召回结果整理为稳定的 `Evidence`、`metadata.answer_rag` 和审计信息。
5. 在依赖缺失、契约不符或无有效命中时明确失败。

### 2.2 明确不承担的职责

回答相关 RAG 不负责以下事项：

1. 决定本轮是否应该回答或追问。
2. 修改问诊状态、会话状态或长期记忆。
3. 通过关键词、正则、默认模板或手写规则补齐回答。
4. 把无审核、无向量或未启用的知识当作可用证据。
5. 直接操作数据库表模型或绕过仓储协议。
6. 代替临床安全裁决或输出安全复核。

### 2.3 知识资产边界

回答相关 RAG 仅依赖现有知识资产承载层，不额外引入第二套生产知识源。

当前的知识边界应理解为：

| 约束 | 含义 |
|---|---|
| 单可信源 | 生产知识仍由既有知识治理链路承载 |
| 启用状态 | 仅使用 `enabled=true` 的知识 |
| 审核状态 | 仅使用 `review_status=approved` 的知识 |
| 向量可用性 | 仅使用 `embedding` 非空的知识 |
| 资产类型 | 仅使用允许进入回答链路的 chunk 类型 |

任务域、宠物资料和会话范围可以参与结构化检索语义，但不应退化为隐式规则集或默认知识源。

## 3. 兼容接口

### 3.1 保持不变的主业务入口

回答相关 RAG 对外不新增独立请求入口，仍然挂接在既有主业务入口之后：

| 接口 | 说明 |
|---|---|
| `POST /agent/turns` | 主业务入口，回答相关 RAG 在后端链路内部触发 |
| `POST /openai/v1/responses` | OpenAI 兼容入口，与主业务入口保持同一回答语义 |

调用方无需为了回答相关 RAG 新增专用字段，也不应依赖隐式关键词来触发回答分支。

### 3.2 保持稳定的协议边界

以下协议和响应信息属于稳定对齐面：

| 对齐项 | 语义 |
|---|---|
| `AnswerRagServiceProtocol` | 调用方依赖的稳定服务协议 |
| `AnswerRagService` | 回答相关 RAG 的服务边界 |
| `AnswerRagResult` | 回答相关 RAG 的结构化结果 |
| `metadata.answer_rag` | 回答相关 RAG 的可观测摘要 |
| `metadata.multi_agent_path` | 链路审计中的执行路径摘要 |
| `evidence` | 面向响应和审计的证据列表 |
| `reasoning_display` | 面向展示的受约束摘要 |

上述字段和协议用于兼容后续实现、测试和审计，不应被替换为临时字段或非结构化文本。

### 3.3 稳定输出约定

回答相关 RAG 的稳定输出应至少包含以下语义：

| 字段 | 说明 |
|---|---|
| `strategy` | 当前回答 RAG 策略标识 |
| `retrieval.query` | 结构化检索查询摘要 |
| `retrieval.hits` | 归一化后的命中列表 |
| `retrieval.top_k` | 本轮召回上限 |
| `retrieval.min_score` | 本轮最低分数阈值 |
| `retrieval.backend` | 检索后端标识 |

后续实现可以调整内部拼装方式，但不得破坏这些对外稳定语义。

## 4. 边界约束与 Fail Fast

回答相关 RAG 的默认原则是：能明确失败，就不要静默回退。

必须显式失败的情况包括：

1. `answerability.decision` 不是 `answer`。
2. 用户输入为空。
3. 结构化请求字段不符合契约。
4. 关键配置非法或缺失。
5. embedding、数据库或检索后端不可用。
6. 无已审核、已启用且达到阈值的有效命中。

不允许重新引入的回退路径包括：

1. 文本相似度兜底。
2. 文件知识兜底。
3. seed 知识兜底。
4. 默认知识命中。
5. 默认回答模板。
6. 关键词回答路径。

这一约束的目的，是降低后续链路的心智负担，并避免让回答相关 RAG 退化成隐式规则机。

## 5. 多任务与审计

回答相关 RAG 允许出现在多任务场景中，但它只对本任务的回答证据负责。

在多任务回合里，回答任务和追问任务可以并存，但它们应分别记录自己的结果，不应相互借用上一个任务的证据或摘要。

回答相关 RAG 相关的审计信息应满足：

1. 能区分回答任务与其他任务。
2. 能回指到本轮实际使用的证据。
3. 能说明本轮没有使用隐式回退。
4. 能支持真实服务联调和回归测试。

## 6. 有意保留的 TODO

以下项是本次迁移阶段有意保留的待办，不代表实现缺失：

| TODO | 说明 |
|---|---|
| 回答知识资产治理界面 | 当前继续沿用既有知识治理链路，未新增独立管理界面 |
| 回答知识质量评测集 | 当前保证契约、审核和可追溯性，尚未建立独立医学评测体系 |
| 更细粒度的引用展示 | 当前只保证 `Evidence` 和 `metadata.answer_rag` 契约 |
| 多语言与多物种知识治理 | 当前以中文宠物问诊为主要范围 |
| 真实 PostgreSQL/pgvector 集成门禁 | 依赖 CI/CD 环境提供数据库和 embedding 服务 |
| 回答知识发布工作流 | 当前依赖既有知识发布链路，未单独建设回答知识发布面 |

这些 TODO 不应通过新增关键词规则、默认模板、文本相似度回退或本地知识兜底提前补齐。

## 7. 后续对齐原则

后续凡是涉及回答相关 RAG 的变更，默认遵守以下原则：

1. 先保持主入口兼容，再扩展响应语义。
2. 先保持协议稳定，再调整内部实现。
3. 任何依赖缺失、契约不符或无有效命中的情况都应直接失败。
4. 不允许恢复旧版默认知识路径、关键词路径或文本相似度回退。
5. 回答相关 RAG 只做证据召回与上下文打包，不做回答充分性裁决。
6. 若后续需要新增字段，应以版本化契约方式扩展，不应复用模糊字段承载额外语义。
