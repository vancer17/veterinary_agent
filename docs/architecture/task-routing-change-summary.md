# 多任务拆分变更总结

> **文档状态**：迁移完成后的对齐基线
>
> **适用范围**：主业务对话入口、多任务拆分、单任务与多任务问诊状态衔接、任务路由审计、真实外部 API 集成测试
>
> **不适用范围**：问诊语义抽取内部实现、问诊槽位状态机、RAG 检索、回复生成策略、长期记忆写入策略、前端多任务完整交互设计和管理后台目录治理

## 1. 变更目的

本次迁移将多任务拆分从旧版关键词和手写 JSON 路径收束为“结构化模型输出 + Pydantic 契约校验 + 数据库任务域目录 + OPA 策略准入 + 不可变执行计划”的任务路由边界。

迁移前，多任务拆分存在以下风险：

1. 任务识别依赖关键词、规则分支或模型自然语言 JSON 文本，容易误判、漏判或解析失败后隐式回退。
2. 任务域与问诊域混用，`consultation_domains.classifier_keywords` 容易继续扩张为业务状态机。
3. 有未完成问诊状态时跳过拆分，导致同一用户输入中的新任务无法被识别。
4. 多任务计划缺少统一策略准入，任务数量、任务域、任务键和既有任务引用分散校验。
5. 生产主路径和测试替身边界不够清晰，后续迁移难以判断某个结果来自真实服务还是本地规则。

迁移后，主链路采用以下边界：

| 能力 | 可信等级 | 位置 | 允许用途 |
|---|---|---|---|
| 用户本轮输入 | 原始输入 | 主业务请求 | 作为任务拆分的唯一自然语言来源 |
| 活跃问诊状态摘要 | 可信运行状态 | PostgreSQL 权威状态读取结果 | 判断是否承接既有任务，不用于生成新任务规则 |
| 任务域目录 | 可信配置数据 | `task_routing_domains` | 限定模型可选择的任务域集合 |
| 结构化任务建议 | 条件可信输入 | LiteLLM `response_format` | 作为任务执行计划的候选输入，必须经契约和策略校验 |
| OPA 任务路由策略 | 可信准入裁决 | `vet_agent.task_routing.decision` | 校验任务计划是否允许进入执行阶段 |
| 任务执行计划 | 可信执行契约 | 主编排层内部 | 决定本轮执行单任务还是多任务，以及每个任务读写哪个状态键 |

多任务拆分只回答“本轮输入应作为一个任务处理，还是拆分为多个可独立执行的任务”。它不负责医学诊断、问诊槽位更新、RAG 检索、回复生成、记忆写入或前端展示编排。

## 2. 职责边界

### 2.1 任务路由职责

任务路由当前负责：

1. 在记忆读取之后、问诊语义抽取之前执行。
2. 消费当前用户输入、可信身份范围、宠物上下文摘要和活跃问诊状态摘要。
3. 从任务域目录中读取允许的任务域集合。
4. 通过结构化模型输出生成一个或多个任务建议。
5. 对任务建议进行 Pydantic 契约校验和本地技术不变量校验。
6. 调用 OPA 任务路由策略执行最终准入。
7. 输出不可变任务执行计划，供主编排器决定单任务或多任务执行。
8. 将任务路由摘要写入响应 metadata，便于调试、前端展示和真实服务验收。

任务路由不负责：

1. 使用关键词、正则、字符串匹配或硬编码规则拆分任务。
2. 根据疾病、症状严重度或临床安全候选决定安全动作。
3. 更新问诊槽位、判断回答充分性或生成追问。
4. 执行 RAG 检索或重排。
5. 读取或写入长期记忆事实。
6. 生成最终自然语言答复。
7. 在模型、数据库或 OPA 不可用时改用本地规则兜底。

### 2.2 主编排层职责

主编排层负责消费任务执行计划，而不是重新拆分或修正计划。

主编排层当前负责：

1. 按任务执行计划选择单任务或多任务路径。
2. 将每个任务的文本片段传递给后续问诊、RAG 和回复生成链路。
3. 按计划指定的任务键读取和保存问诊状态。
4. 合并多任务响应分段、整轮 reasoning display 与 metadata。
5. 在多任务计划承接旧默认状态时执行状态键迁移。

主编排层不负责：

1. 二次猜测任务域。
2. 在任务计划非法时尝试自动修复。
3. 将任务路由失败降级为普通单任务。
4. 在多任务之间共享未隔离的问诊状态。
5. 把任务路由 metadata 当作医学结论。

### 2.3 OPA 策略职责

OPA 是任务计划进入执行阶段前的策略准入点，但不是自然语言拆分器。

OPA 当前负责：

1. 校验任务列表非空。
2. 校验任务数量不超过上限。
3. 校验任务域来自数据库目录。
4. 校验任务键非空且不重复。
5. 校验任务文本长度有效。
6. 校验 `existing_task_key` 只能引用当前活跃任务。
7. 输出允许或拒绝动作、原因和审计信息。

OPA 不负责：

1. 读取或扫描原始用户自然语言。
2. 创建任务、改写任务文本或补全任务域。
3. 维护关键词库、问诊状态机或临床安全规则。
4. 访问业务数据库、Mem0、RAG 知识库或模型服务。
5. 决定任务执行顺序之外的医学优先级或安全升级动作。

## 3. 数据链位置

多任务拆分位于当前 Agent 主数据链的固定位置：

```text
基础输入安全
-> 宠物上下文加载
-> 临床安全语义抽取
-> 临床安全候选召回
-> 临床安全裁决
-> 记忆读取
-> 多任务拆分
-> 问诊语义抽取
-> 问诊状态更新
-> RAG 检索
-> 回复生成
-> 输出安全复核
-> 记忆写入候选
-> 回合留痕
```

该顺序的含义是：

1. 多任务拆分不会绕过输入安全、范围授权或临床安全裁决。
2. 多任务拆分可以看到活跃问诊状态摘要，但不直接维护长期记忆。
3. 后续问诊、RAG 和回复生成按任务执行计划分别处理任务文本。
4. 多任务拆分失败时，本轮不继续进入问诊状态更新或普通回答生成。

后续迁移问诊状态、RAG、回复生成或记忆写入时，应把任务执行计划视为上游已校验事实，不应重新引入关键词拆分或默认单任务回退。

## 4. 接口兼容边界

### 4.1 已覆盖的主业务入口

以下入口继续使用既有请求结构，不要求调用方新增多任务字段：

| 接口 | 状态 | 说明 |
|---|---|---|
| `POST /agent/turns` | 已覆盖 | 主业务对话入口，多任务拆分在后端主链路内部执行 |
| `POST /openai/v1/responses` | 已覆盖 | OpenAI Responses 风格兼容入口，与主业务入口使用同一任务路由语义 |

调用方仍按既有契约提交 `input`、`scope_assertion`、`vet_context`、`attachments`、`metadata`、`turn_options` 和 `stream`。多任务拆分不要求调用方预先声明“这是多任务”。

### 4.2 保持兼容的请求字段

以下字段为兼容保留，不属于本次多任务拆分迁移的变更面：

| 字段 | 兼容策略 |
|---|---|
| `input` | 继续作为任务拆分、问诊语义抽取和回复生成的用户输入来源 |
| `scope_assertion` | 继续作为可信用户、宠物和会话范围来源 |
| `vet_context.pet_info` | 继续作为未验证宠物资料兼容字段，不参与任务域权威判断 |
| `attachments` | 继续由输入安全和后续能力边界处理，任务路由不解析附件内容 |
| `metadata` | 继续作为审计透传字段，不得作为任务路由规则来源 |
| `model` | 继续影响模型选择，不改变任务路由契约 |
| `turn_options.idempotency_key` | 幂等语义保持不变 |
| `turn_options.max_followup_questions` | 后续问诊阶段继续使用，任务路由不改变其含义 |
| `stream` | 同步与 SSE 流式响应开关保持不变 |

后续如需调用方显式控制任务路由行为，应通过独立接口契约评审，不应复用 `metadata` 或未验证 `vet_context.pet_info` 作为隐式控制项。

### 4.3 稳定的响应可观察字段

多任务拆分通过响应结构和 metadata 对外可观察。

| 字段或行为 | 语义 |
|---|---|
| `vet_result.route=consultation` | 本轮按单任务问诊路径执行 |
| `vet_result.route=multi_task_consultation` | 本轮按多任务问诊路径执行 |
| `segments[]` | 多任务响应的任务分段；单任务响应可为空或按既有语义保留 |
| `segments[].reasoning_display` | 单个任务分段对应的可展示推理摘要 |
| `reasoning_display.metadata.kind=user_visible_multi_task_routing` | 整轮多任务路由展示摘要 |
| `metadata.task_router` | 任务路由策略、任务数量、任务域和执行计划摘要 |
| `metadata.multi_agent_path` | 应包含 `TaskRouterAgent`，用于审计任务路由阶段确实经过主链路 |
| `metadata.consultation_state` | 单任务或当前聚合视角下的问诊状态摘要 |
| `metadata.consultation_states` | 多任务场景下按任务键组织的问诊状态集合 |
| `metadata.memory_read` | 任务路由前完成的记忆读取审计摘要 |

后续前端或 BFF 可以依赖上述字段进行多任务展示和排障，但不应依赖内部类名、提示词内容、Rego 规则体、测试替身或模型原始响应。

## 5. 任务域目录边界

任务域目录由 `task_routing_domains` 表承载，定位是“任务路由可选域目录”，不是问诊状态机，也不是临床规则库。

目录当前表达：

| 字段 | 语义 |
|---|---|
| `domain` | 稳定任务域标识 |
| `title` | 面向展示和审计的任务域标题 |
| `description` | 面向模型结构化输出的任务域职责说明 |
| `priority` | 同一轮多个任务的排序参考 |
| `enabled` | 是否进入运行时允许目录 |
| `version` | 目录版本 |
| `metadata` | 附加审计信息 |

目录不保存：

1. 关键词、正则、同义词或示例句规则。
2. 临床安全动作。
3. 问诊槽位流转条件。
4. RAG 检索策略。
5. 前端展示模板。
6. 记忆写入策略。

目录治理原则：

1. `domain` 应保持稳定，不应因展示名称调整而变更。
2. 新增任务域必须同步更新 Alembic 基线、seed 入口、OPA 测试、单元测试、真实服务集成测试和本文档。
3. 禁用任务域应通过 `enabled=false` 表达，不应删除历史审计需要理解的域标识。
4. 不应把任务域目录扩展为“自然语言分类规则表”。

## 6. 问诊状态键边界

多任务拆分与问诊状态的关系只限于“读写哪个状态键”。

当前状态键语义如下：

| 场景 | 状态键策略 |
|---|---|
| 单任务且无多任务状态 | 使用 `__default__` |
| 单任务承接已有默认问诊 | 继续使用 `__default__` |
| 多任务中新建任务 | 使用任务计划中的具体 `task_key` |
| 多任务承接已有具体任务 | 使用对应具体 `task_key` |
| 旧默认状态参与多任务计划 | 读取 `__default__`，写入具体任务键，并清理旧默认状态 |

旧默认状态迁移的目的，是避免同一组问诊状态同时出现在 `__default__` 与具体任务键下。它只处理状态存储位置，不改变医学语义，不判断问诊槽位，也不构成新的状态机。

后续问诊状态迁移应遵守以下边界：

1. 问诊槽位更新继续由问诊状态链路负责。
2. 多任务拆分不得直接修改槽位含义。
3. 任务键只用于隔离不同任务的问诊状态，不代表诊断类别。
4. 清理默认状态只发生在明确迁移到具体任务键后。

## 7. 降级与 Fail Fast 规则

多任务拆分迁移后的核心原则是：依赖、契约或策略失败时，不启用本地硬编码任务拆分回退。

允许的降级：

1. 测试或特殊嵌入场景可以显式注入静态任务域仓储和本地策略替身。
2. 模型输出一个合法单任务计划时，主链路按单任务执行。
3. 用户输入本身只有一个问题时，主链路按单任务执行。
4. 任务域目录中禁用的任务域不进入运行时允许集合。

不允许的降级：

1. 不允许模型调用失败时改用关键词拆分。
2. 不允许结构化输出非法时从自然语言响应中截取 JSON。
3. 不允许任务域目录为空时使用内置默认目录继续生产运行。
4. 不允许 OPA 不可用时回退本地策略。
5. 不允许 OPA 返回非法结构时宽松修复并继续执行。
6. 不允许因存在未完成问诊状态而跳过任务路由。
7. 不允许根据 `vet_context.pet_info` 或 `metadata` 补造任务域。

Fail Fast 场景：

| 场景 | 预期行为 |
|---|---|
| 用户输入为空 | 拒绝进入任务路由 |
| 任务域目录为空或不可用 | 主链路失败 |
| 结构化模型不可用 | 主链路失败 |
| 模型输出不符合 schema | 主链路失败 |
| 模型返回未知任务域 | 主链路失败 |
| 模型返回空任务文本 | 主链路失败 |
| 模型返回重复任务键 | 主链路失败 |
| 模型引用未知活跃任务键 | 主链路失败 |
| OPA 策略不可用 | 主链路失败 |
| OPA 策略拒绝任务计划 | 主链路失败 |
| OPA 返回非法结构 | 主链路失败 |

## 8. 已移除的生产路径

以下路径不再属于生产数据链：

1. `TaskSplitterAgent`
2. `RuleTaskSplitter`
3. `src/vet_agent/agents/task_splitter.py`
4. `ConsultationDomainModel.classifier_keywords`
5. 基于关键词的任务域判断
6. 手写 JSON 文本截取和 Markdown code fence 兼容解析
7. 因存在未完成问诊状态而跳过任务路由的路径
8. 任务路由失败后自动退回普通单任务的隐式兜底

如果后续代码重新引入上述模式，应视为架构回退，需要在设计评审中明确说明原因、边界和退出计划。

以下 TODO 是本次迁移有意保留的工程边界，用于避免多任务拆分继续扩张为自定义规则状态机。

| TODO | 边界说明 | 后续建议 |
|---|---|---|
| 任务域目录治理接口 | 当前目录通过 Alembic 和 seed 基线维护，没有实现管理后台编辑、审核、版本发布和回滚 | 后续在管理后台或运维脚本中增加目录治理流程，保持 `domain` 稳定，避免业务代码内置目录变更 |
| 更细任务域层级 | 当前任务域保持粗粒度，主要用于状态隔离和多任务展示，不承担临床诊断分类 | 后续如需二级域或标签，应新增独立字段或目录，不应恢复关键词分类 |
| 任务优先级策略增强 | 当前排序主要使用目录优先级和模型输出优先级，不实现复杂医学优先级矩阵 | 后续可由 OPA 基于结构化任务元数据增强排序或准入，但不得扫描自然语言 |
| 并行任务执行 | 当前多任务可以形成多个分段，但执行仍以主编排层可控顺序完成 | 后续如引入并行执行，应先定义事务、幂等、状态写入和响应合并边界 |

| 流式终态 metadata 对齐 | 已有工单记录流式终态 metadata 完整性问题，多任务字段需要纳入同一对齐范围 | 后续在 SSE 终态统一补齐 `task_router`、`consultation_states` 和分段摘要 |
| 任务级 RAG 与上下文预算 | 当前任务分段可分别进入后续链路，但尚未建立任务级上下文预算策略 | 后续在 RAG 和回复生成迁移时引入任务级预算，不应回到全局拼接 |
| 任务级记忆读取过滤 | 当前记忆读取发生在任务路由前，任务级记忆上下文编译尚未单独建模 | 后续结合 Mem0 和权威事实读取，引入任务级 MemoryContextBuilder |
| 任务路由真实服务门禁常态化 | 当前提供手动 try-run 外部 API 门禁，不放入默认全量 CI | 后续在 GitHub Environment 密钥稳定后，可在发布前强制执行 `task-routing-api` 或聚合 `external-api` |
| OPA 策略观测增强 | 当前策略返回允许或拒绝及原因，尚未建立集中化 decision log 分析面板 | 后续由运维或观测链路接入 OPA decision log，不在业务代码中重复记录策略细节 |

## 10. 明确不做事项

为了保持本次迁移边界清晰，以下事项不属于当前阶段：

1. 不把任务路由改造成临床诊断分类器。
2. 不在任务路由中实现问诊槽位状态机。
3. 不在任务路由中执行临床安全升级、阻断或用药判断。
4. 不让 OPA 扫描用户自然语言。
5. 不让 PostgreSQL 任务域目录保存关键词规则。
6. 不让 Mem0 召回结果直接决定任务拆分。
7. 不让 RAG 命中结果反向修改任务计划。
8. 不在模型失败时回退本地关键词或默认规则。
9. 不通过 `metadata`、`vet_context.pet_info` 或附件内容隐式控制任务路由。
10. 不在本次迁移中重写前端多任务完整视图。

## 11. 生产装配与配置边界

生产容器默认使用：

| 配置或依赖 | 当前语义 |
|---|---|
| `DATABASE_URL` | 读取 `task_routing_domains` 和问诊状态等 PostgreSQL 权威数据 |
| `QWEN_MODEL` | 通过 LiteLLM 执行结构化任务路由模型调用 |
| `TASK_ROUTING_MAX_TASK_COUNT` | 限制单轮最多任务数量 |
| `TASK_ROUTING_OPA_BASE_URL` | OPA Data API 基础地址 |
| `TASK_ROUTING_OPA_PACKAGE_PATH` | 默认 `vet_agent.task_routing` |
| `TASK_ROUTING_OPA_RULE_NAME` | 默认 `decision` |
| `TASK_ROUTING_OPA_AUTH_TOKEN` | 可选 OPA 鉴权 token |

配置边界：

1. 生产容器不应自动使用静态任务域仓储或本地策略客户端。
2. 测试替身必须通过显式依赖注入进入，不能由生产配置静默回退。
3. 任务路由配置不应承载临床安全、RAG、记忆写入或前端展示配置。
4. 任务域目录变更应通过数据库迁移或受控 seed 流程完成。

## 12. 真实服务集成测试边界

当前多任务拆分已提供真实外部 API 冒烟测试入口：

| 入口 | 作用 |
|---|---|
| `tests/integration/test_task_routing_api_external.py` | 通过真实 PostgreSQL、LiteLLM 与 OPA 验证多任务拆分纵向链路 |
| `scripts/integration/run-task-routing-api-smoke.sh` | 通过 SSH 隧道建立远程依赖连接并运行测试 |
| `scripts/ci/try-run.sh task-routing-api` | 手动执行多任务拆分真实服务门禁 |
| `scripts/ci/try-run.sh external-api` | 聚合执行当前已迁移的真实服务主路径 |

测试边界：

1. 默认 CI 不会自动触发真实外部服务测试，避免缺少密钥或网络波动污染普通门禁。
2. 开启真实测试时必须显式配置数据库、LiteLLM、OPA 和 SSH 隧道相关环境变量。
3. 多任务拆分测试刻意不启用真实 Mem0，以避免把任务路由问题与语义记忆投影问题混在一起。
4. 测试会写入带唯一前缀的最小运行数据，并在结束时清理。
5. 测试要求远程数据库至少迁移到 `0014_task_routing_domain_catalog`。

## 13. 后续领域对齐原则

后续迁移问诊状态、RAG、回复生成、输出安全和记忆写入时，应遵守以下原则：

1. 任务执行计划是任务拆分阶段的唯一可信输出。
2. 后续模块只消费计划，不重新拆分用户输入。
3. 每个任务应独立维护问诊状态、RAG 上下文和回复分段。
4. 跨任务共享的内容必须来自可信宠物画像、权威记忆事实或显式全局上下文，不得来自某个任务的临时槽位。
5. 策略调整优先进入 OPA 或目录治理，不进入 Python 关键词分支。
6. 真实服务门禁应覆盖模型结构化输出、数据库目录、OPA 策略和主 API metadata，而不是只验证本地替身对象。
