# 追问相关 RAG 变更总结

> **文档状态**：迁移完成后的对齐基线
>
> **适用范围**：问诊回答充分性 `ask` 分支、追问计划生成、RAG 知识召回、响应审计、真实服务集成测试
>
> **不适用范围**：问诊状态机本身、临床安全裁决、长期记忆写入、任务路由、输出安全复核、管理后台知识治理完整实现

## 1. 变更目的

本次迁移的目标，是将“追问该问什么”从旧版默认模板、关键词路径、正则规则和手写回退中收束出来，改为由回答充分性裁决、已审核知识召回和结构化追问计划共同驱动。

迁移后的核心变化不是增加一个新的业务状态机，而是明确三层职责：

| 能力 | 职责 |
|---|---|
| OPA 回答充分性裁决 | 决定本轮是否进入 `ask`，并给出本轮必须补充的高价值槽位 |
| 追问相关 RAG | 只负责从已审核知识中召回证据，并生成符合契约的追问计划 |
| 问诊状态服务 | 只在追问计划校验通过后记录已经问出的追问问题 |

## 2. 作用边界

### 2.1 本次迁移允许依赖的内容

追问相关 RAG 当前只允许依赖以下输入和输出：

| 类型 | 边界 |
|---|---|
| 入口条件 | 仅在回答充分性裁决结果为 `ask` 时进入 |
| 必要槽位 | 仅消费 `missing_slots`，不自行扩展槽位集合 |
| 可信上下文 | 仅消费宠物可信摘要、问诊状态快照和当前用户输入 |
| 知识来源 | 仅召回已审核、已启用、可向量检索的 `knowledge_chunks` |
| 输出形式 | 返回结构化追问计划、知识证据摘要和可审计 metadata |
| 错误语义 | 依赖缺失、契约不符或无有效命中时直接 Fail Fast |

### 2.2 明确不承担的职责

追问相关 RAG 不负责以下事项：

1. 决定本轮是否应该追问。
2. 生成或维护问诊状态机。
3. 在缺少证据时使用默认模板、关键词、正则或 seed 回退补齐问题。
4. 把未验证的 `vet_context.pet_info` 直接提升为权威事实。
5. 直接写入活跃问诊状态之外的长期事实库。
6. 代替 OPA 决定回答、追问、放行或升级。

### 2.3 当前知识资产边界

追问相关 RAG 只读取现有 `knowledge_chunks` 资产，不引入第二套生产知识表。

这意味着：

| 约束 | 含义 |
|---|---|
| 单可信源 | 追问知识资产仍由现有知识治理链路承载，不再建立独立私有表 |
| 资产过滤 | 仅使用启用且审核通过的向量 chunk |
| chunk 类型 | 当前默认仅接纳 `followup_questions` 语义资产 |
| 证据可追溯 | 追问计划必须能回指到具体证据标题和 chunk 标识 |

## 3. 兼容接口

### 3.1 保持不变的主业务入口

以下接口不需要调用方新增追问字段：

| 接口 | 说明 |
|---|---|
| `POST /agent/turns` | 主业务入口，追问相关 RAG 在后端内部触发 |
| `POST /openai/v1/responses` | OpenAI 兼容入口，追问语义与主业务入口一致 |

### 3.2 保持稳定的响应字段

追问相关 RAG 对外稳定暴露以下响应信息：

| 字段 | 语义 |
|---|---|
| `metadata.followup_question_plan` | 结构化追问计划摘要 |
| `metadata.missing_slots` | 本轮 OPA 认可的缺失槽位 |
| `metadata.multi_agent_path` | 可观测的链路节点集合 |
| `segments[].type` | 追问场景下通常为 `followup_consultation` |
| `evidence` | 追问相关知识证据列表 |

### 3.3 保持稳定的可观测标识

以下标识用于审计和测试，不应被后续模块替换为隐式约定：

| 标识 | 语义 |
|---|---|
| `FollowupRagStrategy.LLAMA_INDEX_PGVECTOR_STRUCTURED` | 当前生产追问策略名称 |
| `FollowupRagService` | 追问相关 RAG 的服务边界 |
| `FollowupRagRetriever` | 追问知识召回边界 |
| `FollowupRagPlanner` | 结构化追问计划生成边界 |
| `FollowupRagServiceProtocol` | 调用方依赖的稳定协议 |

## 4. 有意保留的 TODO

以下项是本次迁移阶段有意保留的待办，不代表实现缺失：

| TODO | 说明 |
|---|---|
| 追问知识资产治理接口 | 当前只要求已有知识资产满足召回契约，未新增独立的追问知识管理 API |
| chunk 类型扩展策略 | 当前默认仅使用 `followup_questions`，后续如需扩展其他追问知识分类，再单独评审 |
| 召回质量观测标准 | 当前只保证可审计和可追溯，尚未把追问召回质量细化为独立指标体系 |
| 多语言或多物种追问模板 | 当前以中文宠物问诊为主，后续如需扩展，应在策略和知识治理层分别对齐 |
| 更细粒度的响应展示规范 | 当前只保证结构化计划和证据可用，未定义更复杂的前端话术分层 |
| 追问知识发布工作流 | 当前依赖现有知识治理链路，未建立单独的发布、回滚和审校界面 |

## 5. 对齐原则

后续凡是涉及追问相关 RAG 的变更，默认遵守以下原则：

1. OPA 决定是否追问，以及必须补充哪些槽位。
2. RAG 只负责召回证据和生成受约束的追问计划。
3. 任何缺失、非法或无命中的情况都应直接失败，不应静默回退。
4. 不引入关键词状态机，不恢复默认模板，不使用 seed 文件作为生产回退。
5. 追问计划只在契约校验通过后写入活跃问诊状态。
6. 对外接口优先保持兼容，内部重构优先遵循单可信源和 Fail Fast 原则。

## 6. 后续协作建议

如果后续要继续实现追问相关能力，建议优先对齐以下内容：

| 优先级 | 建议 |
|---|---|
| 高 | 继续收敛追问知识资产的发布契约和审计口径 |
| 高 | 继续保持 OPA 与 RAG 的职责分离 |
| 中 | 继续补充真实服务集成测试和可观测断言 |
| 中 | 继续统一响应 metadata 的展示口径 |
| 低 | 再考虑多语言、模板变体或更细粒度的前端呈现 |
